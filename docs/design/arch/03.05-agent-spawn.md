# Agent Spawn — SubAgent 与 BackgroundAgent 派生执行

---

## § 职责定位

`AgentSpawnDispatcher` 负责统一处理 Agent Runtime 中的派生执行请求，不负责 LLM 迭代本身。

它覆盖两类场景：

- 主 Agent 通过工具发起的 SubAgent / BackgroundAgent
- Scheduler / System 直接发起的 BackgroundAgent root run

---

## § 核心原则

**概念层保留区分**：`SubAgent` 表示“由另一个 Agent 发起并等待结果的派生执行”；`BackgroundAgent` 表示“以 detached 方式运行的后台执行”。

**实现层共享机制**：SubAgent 与 BackgroundAgent 共用同一个 `AgentRunner` 和同一套 spawn 机制；差异主要在 `InvocationMode`、发起源和结果交付方式。

**LLM 不直接构造其他 Agent**：主 Agent 只能通过 orchestration tool 请求派发；真正的派生执行由 Runtime 的 spawn 层控制。

---

## § 概念与运行方式

| 概念 | 典型发起方 | InvocationMode | 是否等待 | 结果去向 |
|------|-----------|----------------|---------|---------|
| SubAgent | 主 Agent | `inline_child` | 父 Agent 等待 | 回填为父 Agent 的 ToolResult |
| BackgroundAgent | 主 Agent / Scheduler / System | `detached` | 不等待 | 写入任务结果，完成后单独通知 |

---

## § 核心对象

**AgentSpawnDispatcher**

- 解析 spawn source
- 校验派发权限
- 解析目标 AgentProfile
- 构建 spawn context seed
- 构建派生 `AgentRunSpec`
- 同步执行或异步入队
- 维护 parent-child / scheduler-root 链路

**SpawnSource**

- `ParentRun(parent_run_id, parent_agent_id)`
- `Scheduler(job_id)`
- `System(reason)`

**SpawnContextSeed**

- `task_brief`
- `relevant_history_summary`
- `workspace_root`
- `constraints`

**SpawnResult**

- `completed(result)`：同步 SubAgent 结果
- `accepted(task_id)`：后台任务已入队

---

## § 调用入口

建议只暴露两个 orchestration tools：

- `delegate_to_agent`
- `spawn_background_agent`

这两个工具都不直接执行 agent，而是把请求交给 `AgentSpawnDispatcher`。

除此之外，Scheduler / System 也可以直接请求 spawn 后台 Agent，而不需要先构造一个“主 Agent 再转委托”。

```mermaid
    participant Runner as AgentRunner
```

```mermaid
    Spawn-->>Scheduler: accepted(task_id)
    Queue->>Runner: run(spec, background_hooks)
```

这里没有“主 Agent 先委托”这个中间层。  
定时任务应直接启动 `BackgroundAgent` root run。

## § 上下文继承规则

默认建议：

**SubAgent 继承**

- 任务描述
- 相关历史摘要
- 工作目录边界
- 必要约束

**SubAgent 不继承**

- 完整对话历史
- 完整记忆库
- 父 Agent 的全部工具权限

**BackgroundAgent 继承**

- 任务 payload
- root session id
- 必要上下文摘要

如果是 Scheduler / System 发起的 BackgroundAgent，则由调度器提供任务 payload，不依赖父 Agent Session。

不建议把整个主 Session 原封不动传给派生执行。

---

## § 权限边界

父 Agent 侧使用 `DelegationPolicy` 控制：

- 能否调 subagent
- 能否调 background agent
- 能调哪些派生 agents
- 最大深度与并发数

目标 Agent 侧使用 `InvocationPolicy` 控制：

- 哪些父 Agent 可以调用它
- 是否继承 workspace scope
- 是否允许结果直接对用户可见

Scheduler / System 发起的 BackgroundAgent 不走父 Agent 的 `DelegationPolicy`，而走 Runtime 级调度权限。

---

## § 并发与深度控制

`delegate_to_agent`（`inline_child`）不占用全局 runner 并发槽，父 Agent 在持有槽的同时等待子 Agent 结果。

`spawn_background_agent`（`detached`）占用全局 runner 并发槽，由 BackgroundTaskManager 调度执行。

深度控制：

- `DelegationPolicy.max_depth` 约束 `inline_child` 委托的最大嵌套层级。
- 每次 `delegate_to_agent` 调用将深度计数加 1；`AgentSpawnDispatcher` 在构建派生 Spec 前检查该计数。
- 超出 `max_depth` 时，Dispatcher 拒绝请求并向父 Agent 返回错误 ToolResult，不静默截断。
- `max_depth = 0` 表示禁止任何委托。

`inline_child` 不占全局槽是为了避免死锁（父 Agent 持槽等待子 Agent，子 Agent 却无法获得槽）。但若不加深度约束，无限嵌套会绕过所有资源控制，因此深度限制是必须的补偿约束。

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| SubAgent 与 BackgroundAgent 是否合并成同一个概念？ | 否，概念层保留区分 | 统一叫 child agent | 二者的发起语义不同，一个强调父 Agent 委托，一个强调 detached 后台执行 |
| 是否共用同一套实现机制？ | 是，共用 spawn 机制 + `AgentRunner` | 两套独立 runtime | 执行链路、权限校验和观测需求高度重叠，没必要复制 |
| 定时任务后台执行是否必须经由主 Agent 委托？ | 否，Scheduler 可直接启动 `BackgroundAgent` | 先构造主 Agent 再委托 | 这会人为引入不存在的父子关系，也让调度链路变脏 |
| 派生执行是否继承完整 Session？ | 否，只传摘要或任务 payload | 复制完整历史 | 完整复制成本高，也容易泄露无关上下文和权限 |
| BackgroundAgent session 是否写 DB？ | Ephemeral（不写 DB） | Persistent（写 DB） | 后台 Agent 的运行状态由 BackgroundTaskManager 追踪（含 task_id、状态、结果）；Session 历史不需长期保留；若 app 崩溃，BackgroundTaskManager 可根据未完成任务重新入队，无需 Session 恢复 |
