> **Status**: `active`

# ContextPipeline — 上下文装配

> 核心命题：定义层给出边界，运行时按请求装配上下文。

---

## § 职责定位

`ContextPipeline` 负责将 Profile、Session、Memory、Knowledge、Inbox、Sources、Skills 和当前输入组装为一次 run 的消息上下文，不负责模型调用、持久化、记忆写入或经验教训生成。

---

## § 核心原则

**稳定内容前置**：稳定内容应放在更前层，尽量复用 Provider cache。Core Layer 的缓存键为 `AgentProfile.id + PromptPolicy 内容哈希`；当 system prompt 内容或 Profile 更新时 Core Layer 缓存失效，Dynamic Layer 和 User Layer 不缓存。

**动态内容按预算注入**：历史、记忆、知识、技能必须受 `ContextPolicy.context_budget` 约束。

**spawn 上下文是摘要，不是复制**：SubAgent 与由主 Agent 派生的 BackgroundAgent 默认只拿到 `SpawnContextSeed`，而不是完整父 Session。

**已确认内容优先**：共有知识和已确认记忆优先于 Inbox 待审核条目；未确认观察默认不进入普通任务上下文。

**分层加载优先**：上下文先走 ContextIndex L0 过滤，再读 Frontmatter `overview` 或 L1 缓存，最后才按需读取 Markdown 正文或原始资源。

---

## § 输入与输出

**输入**

- `AgentProfile`
- `AgentSession`
- `InboundMessage`
- ContextIndex / Memory / Knowledge / Inbox / Sources / Skills 查询结果

**输出**

- `system_prompt`
- `messages`
- `fragments`
- `token_estimate`

这些结果被 AgentLoop 用于构建 `AgentRunSpec`。

---

## § 分层

```text
Core Layer
- Profile system prompt
- Stable instructions
- Tool capability summary

Dynamic Layer
- Session history and session archive references
- Confirmed memory recall
- Knowledge, Inbox and source recall
- Skills injection
- Pending child results

User Layer
- 当前输入
- 运行时上下文
```

---

## § 记忆与知识召回边界

ContextPipeline 接收的是召回结果，不直接访问 Memory、Inbox、Vault、sources 或 SQLite 表的内部存储。所有知识、待处理条目、来源、记忆和演化资产都通过 ContextURI 引用。

召回优先级：

1. 与当前任务匹配的共有知识 L0/L1
2. 已确认的用户偏好、约束和背景记忆 L0/L1
3. 已确认的 Agent 经验、流程和案例记忆 L0/L1
4. 用户明确引用或当前 Inbox / Review 工作域中的 Inbox 条目 L1
5. 指向共有知识的 `shared` 记忆引用
6. 低置信记忆，仅在需要提醒风险时注入

默认排除：

- `pending` 状态且未被用户明确引用的 Inbox 审核候选
- 已拒绝或已删除记忆
- Private 路径下的任何内容
- 未确认经验教训候选正文
- 未完成解析的 Inbox 导入条目正文

当召回项带有知识引用时，ContextPipeline 优先注入知识笔记的 `overview` 和必要正文片段，而不是复制 Memory 中的短摘要。外部原始资料只有在用户当前任务明确依赖来源细节时才进入 L2 读取；解析结果优先通过 Inbox 条目读取。

### 分层读取流程

1. 使用当前输入、工作域、打开文件和权限策略查询 ContextIndex。
2. 基于 L0 字段过滤 `source`、`tags`、`asset_kind`、`status` 和路径。
3. 读取候选的 Frontmatter `overview` 或 L1 缓存，判断是否相关。
4. 在预算允许且相关性成立时，读取 L2 正文或资源解析内容。
5. 输出带 ContextURI、来源、状态和引用边界的上下文片段。

---

## § 与 AgentProfile 的关系

Profile 本身不构建消息，但提供约束：

- `PromptPolicy` 决定 system prompt 模板
- `ContextPolicy` 决定预算、历史、记忆、知识、技能是否启用
- `SecurityPolicy` 决定哪些上下文来源可见

因此 ContextPipeline 是 Runtime 组件，而不是 Profile 的一个字段包。

---

## § spawn context seed

当 `AgentSpawnDispatcher` 派生执行时，ContextPipeline 不复用完整主上下文，而是生成：

- `task_brief`
- `relevant_history_summary`
- `constraints`
- `workspace_root`

这个 seed 会作为派生 run 的初始上下文。

---

## § 关键流程

1. AgentLoop 解析 Profile
2. ContextPipeline 读取 `PromptPolicy` 与 `ContextPolicy`
3. 组装 Core Layer
4. 查询 ContextIndex 并读取候选 L1
5. 按预算读取必要 L2 并组装 Dynamic Layer
6. 注入当前用户输入
7. 输出 `BuiltContext`

---

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| 上下文是否属于 AgentProfile？ | 否，Profile 只提供策略 | 把完整上下文塞进 Agent | 上下文是请求级、Session 级动态数据，不能变成静态定义的一部分 |
| 派生执行是否复制主上下文？ | 否，使用 spawn context seed | 完整复制主 Session | 避免冗余 token 与权限泄露，派生 run 的目标通常更窄 |
| 技能和知识在哪层注入？ | Dynamic Layer | Core Layer | 技能激活和知识检索都是请求相关，放 Core 会导致 cache 失效和 token 浪费 |
| 未确认观察是否注入普通上下文？ | 默认否，只在 Inbox / Review 工作域或用户明确引用时读取 | 把观察候选直接作为记忆注入 | 候选尚未通过审核，直接影响行动会污染长期行为 |
| 召回是否直接读取全文？ | 否，使用 L0/L1/L2 分层加载 | 检索命中后直接注入正文 | 降低 token 浪费，并保留用户可审阅的引用路径 |
