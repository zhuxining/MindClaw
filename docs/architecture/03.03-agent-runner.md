# AgentRunner — run 级执行引擎

---

## § 职责定位

`AgentRunner` 负责驱动一次 run 内部的 `LLM ↔ Tool` 迭代循环，不负责 Session 管理、消息路由、上下文构建或持久化。

---

## § 核心原则

**无业务状态**：Runner 不持有 Session、MessageBus、Channel 或跨次请求业务状态。同一实例可被主对话、子代理和后台代理共用；run 内部的 Rig hook state 只在一次执行期间存在。

**只消费契约**：Runner 的输入是 `AgentRunSpec`，输出是 `AgentRunResult`；它不理解 `InboundMessage` 或 `AgentProfile`。

**Rig 接管执行循环**：Runner 只负责把 MindClaw run 契约适配成 Rig Agent 请求；model ↔ tools 的多轮循环、tool result 回填和最终 history 由 Rig 驱动。

---

## § 边界与对象

**输入**

- `AgentRunSpec`
- 本次 run 的 `ToolDyn` 工具范围
- MindClaw observer（`RunHooks`）
- `CancellationToken`

**输出**

- `AgentRunResult`
- 可选的 Hooks 生命周期事件

**核心对象**

**RigPromptHook**：Rig `PromptHook` 的 MindClaw 适配层，负责文本增量、工具开始/结束、取消、错误策略和 MessageBus 状态桥接。

**ToolSet / ToolServerHandle**：Runner 将本次工具范围加载到 Rig `ToolServer`，由 Rig Agent 在多轮执行中调用。

---

## § Retry Policy（LLM 调用重试）

Runner 在 LLM 调用失败时自动重试 transient error（瞬态错误）。

### RetryMode 枚举

- `Standard`：最多 3 次重试（默认）
- `Persistent`：无限重试瞬态错误（后台任务使用）
- `Disabled`：禁用重试（测试使用）

### RetryPolicy 配置字段

- `max_attempts`：最大重试次数
- `base_delays`：基础延迟序列（指数退避）
- `max_delay`：最大延迟上限
- `transient_markers`：瞬态错误标识符

### 瞬态错误识别

以下错误被识别为瞬态（可重试）：HTTP 429、500/502/503/504、timeout、connection error、”overloaded”、”temporarily unavailable”。

### Retry-After 解析

从错误消息中提取 `Retry-After` 时间，支持 “retry after 30s”、”try again in 500ms”、”wait 2 minutes” 等格式。

### 不同场景默认值

| 场景 | RetryMode |
|------|-----------|
| 主 Agent（Interactive） | Standard |
| SubAgent（InlineChild） | Standard |
| Background Agent（Detached） | Persistent |
| 测试 | Disabled |

## § 核心依赖

Runner 持有（按架构文档）：

- `AgentModelSet` — 已解析的主模型与轻量模型
- `RigPromptHook` — 将 Rig 执行节点桥接到 MindClaw observer
- `ToolServerHandle` — 本次 run 的 Rig 工具执行入口

Runner 不持有：

- `SessionManager`
- `ContextPipeline`
- `MessageBus`
- `AgentRegistry`
- `Storage`

### 模型解析流程

1. `ModelRouter::resolve(profile)` → 模型名称（Definition 层）
2. `AgentRunSpec.model = “claude-sonnet-4-6”` → 传入 Runner
3. `ProviderRegistry::create_agent_models_from_env(config)` → `AgentModelSet { main, light }`（Adapter 层）
4. `AgentRunner` 根据 `spec.model` 在主模型 / 轻量模型中选择
5. 泛型函数构建 Rig `Agent<M>` + `StreamingPromptRequest`，由 Rig 驱动多轮循环

Provider name 不进入 Runner 构造入口；`LLMCompletionModel` 不再暴露 `complete()` / `stream()` 二次封装 API。

---

## § 关键流程

1. 接收 `AgentRunSpec`
2. 将 MindClaw `ChatMessage` 转为 Rig `Message`
3. 用 `ToolSet::from_tools_boxed()` 装载本次工具范围，并挂到 `ToolServerHandle`
4. 用 `AgentBuilder` 设置 name、preamble、temperature、max_tokens、tool_choice、max_turns 和 hook
5. 用 `StreamingPromptRequest::from_agent(...).with_history(...).multi_turn(...).with_hook(...)` 启动执行
6. `RigPromptHook` 将文本增量、工具状态、取消和错误策略桥接给 MindClaw observer
7. 若遇到瞬态错误，根据 `RetryPolicy` 自动重试
8. 将 Rig final response/history 转换为 `AgentRunResult`

---

## § 多轮迭代与多轮工具执行

多轮迭代和多轮工具执行是 Execution Kernel 的核心职责：

- Rig 维护 model ↔ tools 的多轮循环
- Rig 维护工具结果回填与最终 history
- `AgentRunSpec.max_iterations` 映射到 Rig max turns
- `RigPromptHook` 只观测执行节点并桥接状态，不反向驱动循环

`RunHooks` 不负责决定”是否继续下一轮”，只负责在节点发生时收到一次通知。

因此：

- 不需要额外的 `MultiIterationHooks`
- 不需要额外的 `ToolLoopManager`
- 不需要把循环控制权下放到外部

---

## § 统一执行引擎

主 Agent、SubAgent、BackgroundAgent 共用同一个 Runner。

区别来自：

- `AgentRunSpec.invocation`
- `RunHooks` 实现
- 外层调度与结果交付方式

这意味着 child/background 不是第二套 Runtime，只是不同调用语义。

---

## § 与 RunHooks 的关系

Runner 不知道消息该发到哪里，也不知道结果如何持久化。它通过 `RigPromptHook` 在执行节点调用 `RunHooks`：

- `on_run_start`
- `on_iteration_start`
- `on_model_request_start`
- `on_model_text_delta`
- `on_model_response_ready`
- `on_tool_batch_start`
- `on_tool_call_start`
- `on_tool_call_finish`
- `on_iteration_finish`
- `finalize_response`
- `on_finish`
- `on_abort`

从而把流式输出、观测和后处理注入到外层。

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| Runner 是否持有 Session 或 Bus？ | 否 | 让 Runner 直接持有基础设施依赖 | 这样可以在主/子/后台/测试场景复用同一个执行引擎 |
| provider 解析何时完成？ | AppRuntimeBuilder 通过 ProviderRegistry 创建 `AgentModelSet`，Runner 只接收模型集合 | Runner 接收 provider name 再解析 | provider 选择停在配置层，Runner 不需要知道当前 provider |
| child/background 是否单独实现执行引擎？ | 否 | 分裂为多个 Runner | 统一引擎减少重复和行为漂移 |
| 多轮迭代由谁管理？ | Rig Agent / StreamingPromptRequest | 继续手写工具循环 | Rig 已提供 streaming、tool calling、tool result 回填和 max turn 控制 |
| Retry 在哪一层处理？ | Runner 层（通过 RetryPolicy） | Provider 层或 Loop 层 | Runner 是唯一执行入口，统一处理重试避免分散 |
