# Observability — 可观测性架构

---

## § 职责定位

Observability 层负责收集、存储和展示 Agent 运行的关键指标和调试信息，不负责业务逻辑执行或数据持久化决策。

---

## § 核心原则

**分层可观测**：用户层面向最终用户，日志层面向开发者，指标层面向运维，调试层面向问题排查。

**可选启用**：详细调试信息只在 debug 模式或显式启用时记录，避免性能开销和隐私风险。

---

## § 边界与实体

**输入**：AgentHook 事件流、Provider 层原始响应、工具执行结果、系统状态变化。

**输出**：UI 实时显示数据、结构化日志、指标存储记录、调试快照文件。

**核心实体**：

**ObservabilityCollector**：可观测性数据的分发中心。
关键属性：事件处理器列表（用户层/日志层/指标层/调试层）、采样配置、隐私脱敏规则。
关系：由 AppRuntimeBuilder 初始化；所有 AgentHook 事件流经此处分发到各层。

**AgentEvent**：可观测的 Agent 运行时事件。
关键属性：事件类型（TokenUsage / ToolExecuted / IterationCompleted / LLMCallStart / Error 等）、时间戳、关联 Session/Turn ID、事件负载。
关系：由 AgentHook 方法产生，由 ObservabilityCollector 消费。

**MetricsStore**：指标数据的持久化存储。
关键属性：SQLite 表（token_usage / tool_calls / iteration_stats）、聚合视图（按天/按 Session）。
关系：供 UI 仪表盘查询；供后台分析任务使用。

## § AgentHook 扩展

Observability 通过扩展 AgentHook 实现数据采集：

```rust
pub trait AgentHook {
    // ... 现有方法

    /// 诊断事件通知
    fn on_event(&mut self, event: AgentEvent);
}

pub enum AgentEvent {
    TokenUsage {
        prompt: usize,
        completion: usize,
        model: String,
    },
    ToolExecuted {
        name: String,
        duration_ms: u64,
        success: bool,
        error: Option<String>,
    },
    IterationCompleted {
        count: usize,
        total_tokens: usize,
    },
    LLMCallStart {
        model: String,
        message_count: usize,
    },
    Error {
        source: ErrorSource,
        message: String,
    },
}
```

**ObservabilityHook**：实现 AgentHook，将所有方法调用转换为 AgentEvent，发送到 ObservabilityCollector。

## § 关键指标定义

| 指标 | 类型 | 来源 | 存储 | 用途 |
|------|------|------|------|------|
| Token 用量 | Counter | AgentHook.after_iteration | SQLite | 成本追踪、预算告警 |
| 工具调用次数 | Counter | AgentHook.before_execute_tools | SQLite | 使用频率分析 |
| 工具调用延迟 | Histogram | ToolRegistry 计时 | SQLite | 性能监控 |
| 工具成功率 | Gauge | ToolRegistry 结果统计 | SQLite | 可靠性监控 |
| LLM 调用延迟 | Histogram | Provider 层计时 | SQLite | 性能监控 |
| 迭代次数 | Histogram | AgentHook.after_iteration | SQLite | 任务复杂度分析 |
| 流式首字节时间 | Histogram | Provider 层计时 | SQLite | 流式响应质量 |

## § 隐私与性能

**隐私脱敏**：
- 用户输入内容不出现在日志层（除非显式启用 debug 模式）
- API Key 始终以 `***` 替换
- 文件路径中的用户名等敏感信息脱敏

**性能控制**：
- 指标层采样：高频事件（如流式 token）采样记录，不记录每个 token
- 调试层开关：仅在 `debug: true` 时写入文件
- 异步写入：所有存储操作异步，不阻塞主流程

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| 可观测性数据如何采集？ | AgentHook 扩展（on_event 方法） | 独立埋点代码侵入业务逻辑 | Hook 是自然的扩展点，已覆盖所有关键生命周期；独立埋点重复侵入代码 |
| 指标存储选什么？ | SQLite（与主库同实例） | Prometheus / InfluxDB 等时序数据库 | 个人应用数据量小，SQLite 足够；外部数据库增加部署复杂度 |
| 流式 token 是否全量记录？ | 采样记录（如每 10 个） | 全量记录 | 流式 token 量极大，全量记录影响性能；采样保留趋势信息 |
| 调试信息如何存储？ | 本地文件（可选启用） | 远程日志服务 | 本地优先设计；远程服务增加隐私风险和依赖 |
| 用户输入是否进入日志？ | 不进入（除非 debug 模式） | 默认记录用于分析 | 保护用户隐私；debug 模式显式启用，用户知情 |
