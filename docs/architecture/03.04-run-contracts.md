# Run Contracts — 执行契约

---

## § 职责定位

Run Contracts 定义 Orchestration Layer 与 Execution Layer 之间的数据与生命周期契约，不负责具体的上下文构建、执行逻辑或持久化逻辑。

---

## § 核心对象

**AgentRunSpec**：一次 run 的冻结执行计划。

**AgentRunResult**：一次 run 的结构化结果。

**RunHooks**：Execution Layer 向外层注入生命周期副作用的接口。

**InvocationMode**：当前 run 的调用语义。

**RuntimeCheckpoint**：运行时中断恢复状态。

**Runtime Events**：执行过程中的对外状态契约。
当前代码只保留：

- `UserVisiblePhase`

命名分层：

| 类型 | 语义层级 | 典型消费者 |
| --- | --- | --- |
| `UserVisiblePhase` | 对外可见的简化状态 | `MessageBus` / Channel / UI |

---

建议字段：

- `run_id`
- `agent_id`
- `session_id`
- `invocation`
- `model`
- `system_prompt`
- `messages`
- `context_docs`

- `max_iterations`
- `parallel_tools`

- `tool_choice`
- `temperature`
- `max_tokens`
- `error_policy`
- `retry_mode` — 新增：LLM 调用重试模式

设计要求：

- 构建后不可变
- 包含执行所需全部上下文
- 不在执行中再做 provider/model 解析

建议字段：

- `run_id`
- `final_text`
- `full_message_chain`
- `tool_events`
- `tools_used`
- `usage`

设计要求：

- 足够供 AgentLoop 完成持久化、发布、观测

## § RuntimeCheckpoint（中断恢复）

当 run 因 `/stop`、超时或崩溃中断时，需要保存运行时状态以便恢复。

### CheckpointPhase 枚举

- `None`：无活跃 checkpoint
- `AwaitingTools`：等待工具执行
- `ToolsCompleted`：工具执行完成，等待下一轮
- `FinalResponse`：最终响应阶段

### RuntimeCheckpoint 字段

- `phase`：当前阶段
- `iteration`：迭代次数
- `model`：使用的模型
- `assistant_message`：中间的 assistant 消息
- `completed_tool_results`：已完成的工具结果
- `pending_tool_calls`：待执行的工具调用（id + name）

### 存储位置

Checkpoint 存储在 `AgentSession.metadata` 中，key 为 `runtime_checkpoint`。

### 恢复流程

1. 新消息到达时检查 `session.get_checkpoint()`
2. 若存在 checkpoint：恢复 `assistant_message` 和 `completed_tool_results`
3. 为 `pending_tool_calls` 生成错误结果
4. 清除 checkpoint 和 pending_user_turn 标记
5. 继续正常处理新消息

## § Runtime Events

`events.rs` 的定位不是业务逻辑，而是 **Agent Runtime 的对外状态协议层**。

它与 `spec.rs` 平级：

- `spec.rs` 定义 run 开始前和结束后的输入输出契约
- `events.rs` 定义 run 过程中可透传给 UI / Channel 的状态契约

Provider streaming 和 provider usage 不再作为 MindClaw `events.rs` 的公开契约存在；Rig completion model 与 `StreamingPromptRequest` 在 Runner 内部消费这些细节。

`events.rs` 主要表达 **Runner hook / Loop → Bus 的用户可见状态**：

- `UserVisiblePhase`

作用：

- `UserVisiblePhase`：表示前端 / Channel 可见的简化状态
- 内部执行细节通过 tracing / metrics 记录，不再定义单独的 `RuntimeEvent` / `RunStage`

命名规则：

- 凡是 `*Usage`，表示 token 或成本统计
- 凡是 `*Phase`，表示对外暴露的简化状态

边界要求：

- `events.rs` 适合保留为独立文件
- 不应并入 `observability.rs`，因为它会被 Bus/UI 直接引用
- 不应并入 `loop_.rs` 或 `runner.rs`，因为它被多个模块共享
- 不应并入 `bus/events.rs`，因为它表达的是 Agent Runtime 状态语义，不是通用总线协议

## § InvocationMode

```text
interactive   -> 用户前台对话
inline_child  -> 同步子代理，结果回父 Agent
detached      -> 后台代理，先返回 task id
```

它影响：

- 是否流式输出给用户
- 结果交付给谁
- Session 持久化策略
- Hooks 实现选择
- Retry 模式选择

## § RunHooks

`RunHooks` 是 MindClaw observer 契约；Rig-facing 适配由 `RigPromptHook` 完成。

建议接口：

```rust
fn streaming_mode(&self) -> StreamingMode
fn on_run_start(&mut self, ctx: &RunStartContext)
fn on_iteration_start(&mut self, ctx: &IterationStartContext)
fn on_model_request_start(&mut self, ctx: &ModelRequestContext)
fn on_model_text_delta(&mut self, delta: &str)
fn on_model_response_ready(&mut self, ctx: &ModelResponseContext)
fn on_tool_batch_start(&mut self, calls: &[ToolCall])
fn on_tool_call_start(&mut self, call: &ToolCall)
fn on_tool_call_finish(&mut self, call: &ToolCall, result: &ToolResult)
fn on_iteration_finish(&mut self, ctx: &IterationFinishContext)
fn finalize_response(&mut self, content: &str) -> String
fn on_finish(&mut self, result: &AgentRunResult)
fn on_abort(&mut self, reason: &RunAbortReason)
```

建议实现：

- `InteractiveRunHooks`
- `SubAgentRunHooks`
- `BackgroundRunHooks`
- `NoopRunHooks`
- `RecordingRunHooks`（测试使用）
- `CompositeRunHooks`（组合器）

---

## § CompositeRunHooks（Hook 组合器）

用于串联执行多个 Hook，实现关注点分离。

### 结构

持有 `Vec<Box<dyn RunHooks>>`，按顺序调用所有 Hook。

### 行为

- 所有 Hook 按顺序调用
- `finalize_response` 为 pipeline：每个 Hook 处理前一个的结果
- 错误隔离：单个 Hook 失败不影响其他 Hook

---

## § 执行节点

建议将 Runner 的生命周期节点显式化：

```text
RunStart
IterationStart
ModelRequestStart
ModelTextDelta
ModelResponseReady
ToolBatchStart
ToolCallStart
ToolCallFinish
IterationFinish
ResponseFinalize
RunFinish
RunAbort
```

`RunHooks` 的方法应直接对应这些节点，而不是使用模糊的 `before_*` / `after_*` 风格命名。

---

## § 多轮迭代与多轮工具执行

多轮迭代和多轮工具执行**需要被管理**，但这项管理属于 `AgentRunner`，不属于 `RunHooks`。

建议规则：

- `AgentRunSpec.max_iterations` 映射到 Rig max turns
- Rig `StreamingPromptRequest` 负责消息链增长、工具结果回填和停止条件
- `RigPromptHook` 在每轮模型调用前后触发 iteration 级节点事件
- 每轮若出现工具调用，`RigPromptHook` 触发 tool batch / tool call 级节点事件
- 若进入下一轮，重复上述流程

因此不需要额外设计：

- `MultiIterationHooks`
- `ToolLoopHooks`
- `RoundManagerHooks`

只需要让 `RunHooks` 在每个执行节点上重复收到带上下文的事件即可。

---

## § 上下文对象

建议为 Hooks 提供稳定的上下文值对象，而不是在方法签名中散落大量参数：

- `RunStartContext`
- `IterationStartContext`
- `ModelRequestContext`
- `ModelResponseContext`
- `IterationFinishContext`
- `RunAbortReason`

这些对象至少应包含：

- `run_id`
- `session_id`
- `agent_id`
- `invocation`
- `iteration`
- `message_count`
- `usage`
- `finish_reason`
- `tool_call_count`

---

## § StreamingMode

建议用 enum，而不是 `wants_streaming() -> bool`：

```text
Disabled
TextOnly
```

这样后续若要增加更细粒度的流式能力，不需要改 trait 语义。

## § 关键流程

```mermaid
sequenceDiagram
    participant Loop as AgentLoop
    participant Hooks as RunHooks
    participant Runner as AgentRunner

    Loop->>Runner: run(spec, hooks)
    Runner->>Hooks: on_run_start
    loop 每次迭代
        Runner->>Hooks: on_iteration_start
        Runner->>Hooks: on_model_request_start
        Runner->>Hooks: on_model_text_delta
        Runner->>Hooks: on_model_response_ready
        alt 有工具调用
            Runner->>Hooks: on_tool_batch_start
            Runner->>Hooks: on_tool_call_start / finish
            Runner->>Hooks: on_iteration_finish
        else 完成
            Runner->>Hooks: finalize_response
            Runner->>Hooks: on_finish
        end
    end
    Runner-->>Loop: AgentRunResult
```

## § 设计决策与权衡

| 决策问题                        | 选择                           | 放弃的替代方案                    | 理由                                                               |
| ------------------------------- | ------------------------------ | --------------------------------- | ------------------------------------------------------------------ |
| Hooks 是否保留？                | 是，保留为 Run Contract 一部分 | 将流式和事件逻辑直接写进 Runner   | Runner 保持无业务基础设施感知，场景差异交给 Hooks                  |
| Spec 是否可变？                 | 否                             | 允许运行中修改                    | 不可变更利于测试、复现和观测                                       |
| InvocationMode 是否独立成字段？ | 是                             | 用多个布尔值拼出语义              | invocation mode 是一等概念，直接决定 child/background 行为         |
| 是否为多轮迭代单独设计新接口？  | 否                             | 为多轮再引入额外 manager/delegate | 迭代控制本就属于 Runner；对外只需暴露带 iteration 上下文的节点事件 |
| Checkpoint 存储位置？           | AgentSession.metadata          | 单独的 checkpoint 表              | metadata 是运行时状态的自然存储位置                                |
| Hook 组合方式？                 | CompositeRunHooks 组合器       | 单一 Hook 实现所有功能            | 组合器实现关注点分离，便于扩展                                     |
