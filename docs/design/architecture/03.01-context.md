# MindClaw 技术架构设计 — Context Pipeline

> 完整架构文档索引见 [README.md](./README.md) | Agent 核心见 [03-agent-loop.md](./03-agent-loop.md)

## Context Pipeline — 可插拔上下文组装

上下文组装采用可插拔 `ContextSource` 管线，调用时机固定为：Session 解析完成、SessionCommand 未命中之后，由 `agent.run()` 内部显式触发（仅在 round 0 之前调用一次）。

---

## 三层分工边界

```
┌─────────────────────────────────────────────────────────────────┐
│ AgentLoop（驱动器）                                              │
│  职责：历史压缩 → 构造 ContextInput → 调用 agent.run()          │
│  产出：ContextInput { inbound, history }（不可变 run 级快照）   │
│  边界：对 round 迭代透明，不感知 Source 细节                    │
├─────────────────────────────────────────────────────────────────┤
│ Agent（大脑）                                                    │
│  职责：调用 ContextPipeline.build() → 驱动 round 循环           │
│  产出：AgentContext { system_prompt, messages, fragments }      │
│  边界：对 session 透明，不持有历史状态                           │
├─────────────────────────────────────────────────────────────────┤
│ ContextPipeline（组装器）                                        │
│  职责：按 priority 遍历 Source → 预算分配 → 组装 AgentContext   │
│  产出：system_prompt（String）+ messages（Vec<ChatMessage>）    │
│  边界：纯组装，无副作用，对 run 内部状态透明                    │
└─────────────────────────────────────────────────────────────────┘
```

**三条边界原则**：

- AgentLoop 对 round 透明 — 只交付 ContextInput，不感知内部迭代
- Agent 对 session 透明 — 不持有 history，不知道 SessionManager 的存在
- ContextPipeline 对 run 透明 — 每次 build() 是纯函数式组装，不依赖 run 状态

**ContextInput 的不可变语义**：

- AgentLoop 在 `dispatch()` 的 `PreparingContext` 阶段构造一次，传给 `agent.run()`
- 整个 run 生命周期内共享，round 间不更新
- `input.history` = run 开始前的历史快照；round 间的 assistant 响应/tool_results 由 Agent 内部 `round_messages` 临时维护，run 结束后由 AgentLoop 通过 `append_turn()` 持久化

## ContextSource Trait 与 Pipeline

```rust
// src-tauri/src/agent/context.rs

pub struct ContextFragment {
    pub role: MessageRole,
    pub content: String,
    pub token_estimate: usize,
    pub label: String,
}

/// 每次 run 的请求级数据，仅含本次请求必须的上下文。
/// 基础设施依赖（memory、db、services）由各 ContextSource 在构造时注入。
/// history 由 AgentLoop 通过 session_mgr.compressed_history() 预提取后传入。
pub struct ContextInput {
    pub inbound: InboundMessage,
    pub history: Vec<ChatMessage>,  // 已压缩的对话历史，由 AgentLoop 预提取
}

#[async_trait]
pub trait ContextSource: Send + Sync {
    fn name(&self) -> &str;
    fn priority(&self) -> i32;
    fn enabled(&self) -> bool { true }
    async fn inject(
        &self, input: &ContextInput, budget: usize,
    ) -> Result<Vec<ContextFragment>, AppError>;
}

/// Agent 发给 Provider 的完整上下文，由 ContextPipeline 组装产出。
pub struct AgentContext {
    pub system_prompt: String,
    pub messages: Vec<ChatMessage>,
    pub fragments: Vec<ContextFragment>,  // 仅供 Observer 审计，不传 Provider
}

pub struct ContextPipeline {
    sources: Vec<Arc<dyn ContextSource>>,
    total_budget: usize,
    budget_allocations: HashMap<String, usize>,
}
```

## AgentLoop 层 — 历史压缩与 ContextInput 构造

### compressed_history() 算法

```
输入：Session { turns, summary, summary_covers_turns }

步骤 1：决定 recent_turns 窗口大小
  window = 5  // 默认近 5 轮

步骤 2：分区
  recent_turns = turns.last(window)
  covered_by_summary = turns[0..summary_covers_turns]  // 摘要已覆盖的部分

步骤 3：早期历史处理
  若 summary 存在（且覆盖所有 early_turns）:
      early_messages = [ChatMessage::user("对话摘要：{summary}")]
  否则（摘要尚未生成或不完整）:
      early_messages = []  // 等待 session-summarize SubAgent 异步补全

步骤 4：展开近期轮次为 ChatMessage
  for turn in recent_turns:
      push ChatMessage { role: User,      content: turn.user_message }
      push ChatMessage { role: Assistant, content: turn.assistant_message }
      // tool_use / tool_result 已嵌入 assistant_message.content blocks 中

步骤 5：估算 token 数 → Level 3 兜底
  estimated = token_estimate(early_messages + recent_messages)
  若 estimated > CONVERSATION_HISTORY_BUDGET (~50K):
      window = 3; 重新执行步骤 2-4
  若仍超预算:
      window = 1; 重新执行步骤 2-4
  若仍超预算（单轮极长）:
      only_summary = [early_messages]  // 放弃 recent，只用摘要
      若无摘要：截断 recent_turns[last].assistant_message

步骤 6：拼接
  输出 = early_messages + recent_messages
```

**摘要的异步生成**：摘要不在 `compressed_history()` 内实时生成（避免阻塞主流程）。当 `session.turns.len()` 超过阈值（如 10 轮）时，AgentLoop 在 `append_turn()` 之后异步触发 `session-summarize` SubAgent，写回 `session.summary` 和 `session.summary_covers_turns`，下次 run 时即可使用。Level 3 兜底是防御性措施，正常情况下 Level 2 摘要应已将早期轮次压缩到可控大小。

### ContextInput 的构造时机

`ContextInput` 在 `dispatch()` 内的 `PreparingContext` 状态下构造，对应 03-agent-loop.md 流水线图的这一阶段：

```
dispatch(inbound_message):
  session_mgr.get_or_create(session_id)          // ResolvingSession
  SessionCommand.intercept(message)               // CheckingSessionCommand
  history = session_mgr.compressed_history(id)   // PreparingContext 开始
  input = ContextInput { inbound, history }       // ← 构造点，之后传给 agent.run()
  agent.run(input, cancel_token)
  session_mgr.append_turn(id, run_output)         // PersistingTurn
```

## System Prompt 组装结构

```
┌─────────────────────────────────────────────────────────────────┐
│ 核心层（SoulSource，启动时加载，始终注入）                        │
├─────────────────────────────────────────────────────────────────┤
│ SOUL.md / USER.md / AGENTS.md / 核心工具 Schema（~1K tokens）  │
├─────────────────────────────────────────────────────────────────┤
│ 身份层（IdentitySource，按 mode 路由）                           │
├─────────────────────────────────────────────────────────────────┤
│ IDENTITY-{mode}.md  （fallback: IDENTITY-default.md）           │
├─────────────────────────────────────────────────────────────────┤
│ 运行时层（RuntimeContextSource，每次 run 动态生成）              │
├─────────────────────────────────────────────────────────────────┤
│ 当前时间 / 平台信息 / 语言偏好                                   │
├─────────────────────────────────────────────────────────────────┤
│ 知识/记忆层（每次 run 按需检索注入）                             │
├─────────────────────────────────────────────────────────────────┤
│ RAGKnowledgeSource    — 检索到的知识片段                         │
│ MemoryRecallSource    — 召回的记忆条目                           │
├─────────────────────────────────────────────────────────────────┤
│ 对话层（注入 messages）                                          │
├─────────────────────────────────────────────────────────────────┤
│ ConversationHistorySource — 对话历史                            │
│ UserMessageSource         — 当前用户消息（末尾）                 │
└─────────────────────────────────────────────────────────────────┘
```

### 内置源映射

各 Source 在构造时注入所需的基础设施依赖（`Arc<...>`），运行时仅接收 `ContextInput`（inbound + history）。

| Source                      | Priority | 默认预算 | 构造依赖                | 注入目标           | 注入方式                                          |
| --------------------------- | -------- | -------- | ----------------------- | ------------------ | ------------------------------------------------- |
| `SoulSource`                | 0        | ~4K      | `Arc<ServiceContainer>` | system_prompt      | 固定加载 SOUL/USER/AGENTS + 所有原生工具 Schema（8 个，含 capability_search），不可削减 |
| `IdentitySource`            | 1        | ~2K      | `Arc<ServiceContainer>` | system_prompt 追加 | 按 `input.inbound.mode` 路由到对应 IDENTITY 文件  |
| `RuntimeContextSource`      | 2        | ~500     | —（运行时生成）         | system_prompt 追加 | 当前时间、平台、语言偏好，inject 时动态生成       |
| `RAGKnowledgeSource`        | 10       | ~10K     | `Arc<DbState>`          | system_prompt 追加 | `search_with_rerank` Top N                        |
| `MemoryRecallSource`        | 20       | ~2K      | `Arc<MemoryManager>`    | system_prompt 追加 | relevance + importance 排序                       |
| `ConversationHistorySource` | 30       | ~50K     | —（来自 input.history） | messages           | 直接注入（AgentLoop 已预压缩）                    |
| `UserMessageSource`         | 100      | ~1K      | —（来自 input.inbound） | messages 末尾      | 始终最后                                          |

**system_prompt vs messages 分离原则**：

- `system_prompt`：身份/指令/知识背景 → 对应 Provider `ChatRequest.system`
- `messages`：对话轨迹 + 当前用户消息 → 对应 Provider `ChatRequest.messages`

知识和记忆属于 Agent 的认知背景（指令的一部分），不是对话的参与者，因此注入 system_prompt 而非 messages。

### IdentitySource 路由机制

`input.inbound.mode` 是路由键，由 Channel 层在构造 `InboundMessage` 时设置（用户显式切换或 Channel 默认值）。

```
IdentitySource.inject(input, budget):
  mode = input.inbound.mode           // 如 "general" | "researcher" | "coder"
  path = "identity/IDENTITY-{mode}.md"
  若文件不存在:
      path = "identity/IDENTITY-default.md"  // fallback
  返回 ContextFragment { content: load(path), label: "identity:{mode}" }
```

身份文件存放于 `ServiceContainer` 管理的 `identity/` 目录，支持用户自定义扩展。每个身份文件描述该模式下 Agent 的行为风格、关注重点和输出约定，SOUL.md 的核心人格始终优先生效。

### RuntimeContextSource 注入内容

```
当前时间：2026-04-01T14:32:00+08:00
平台：macOS 25.4 / Tauri 2.x
语言偏好：zh-CN
```

无外部依赖，inject 时实时生成，token 消耗极小（~100-200 tokens）。语言偏好从 `AppConfig` 读取（用户设置），默认跟随系统 locale。

## ContextPipeline.build() 完整算法

```
ContextPipeline.build(input: &ContextInput) -> Result<AgentContext>:

// 阶段 1：预算分配
  total_budget   = pipeline.total_budget          // 由 Provider max_tokens 配置注入
  allocations    = pipeline.budget_allocations    // 各 Source 的预设上限

// 阶段 2：按 priority 顺序调用各 Source
  system_prompt_parts: Vec<String> = []
  messages: Vec<ChatMessage> = []
  fragments: Vec<ContextFragment> = []
  used: HashMap<String, usize> = {}

  for source in sources.sorted_by_priority():
    if !source.enabled(): continue
    budget = allocations[source.name()]
    if total_used() + budget > total_budget:
        budget = remaining_budget()
        if budget < MIN_USEFUL_BUDGET: break  // 预算耗尽，停止注入

    frags = source.inject(input, budget).await?
    used[source.name()] = frags.total_tokens()

    match source.inject_target():
      SystemPrompt => system_prompt_parts.extend(frags.map(|f| f.content))
      Messages     => messages.extend(frags.map(|f| ChatMessage::from(f)))

    fragments.extend(frags)  // 统一收集，供 Observer 使用

// 阶段 3：拼装 system_prompt
  // 结构：SOUL \n\n USER \n\n AGENTS \n\n IDENTITY-{mode} \n\n [运行时上下文] \n\n [RAG 知识] \n\n [记忆摘要]
  system_prompt = system_prompt_parts.join("\n\n")

// 阶段 4：组装 AgentContext
  return AgentContext { system_prompt, messages, fragments }
```

**fragments 的用途**：不传入 Provider，仅用于 `AgentEvent.ContextBuilt` 事件（报告各 Source 的 token 消耗分布），供 Observer 做性能监控与调试。

## Token 预算分配

**total_budget 来源**：由 Provider 配置的 `max_context_tokens`（区别于 `max_output_tokens`）在 `ContextPipeline` 构造时注入，各 Source 按预设比例分配。

**超预算时的三步削减**（`SoulSource`、`IdentitySource`、`RuntimeContextSource`、`UserMessageSource` 免削减）：

```
步骤 1：削减 RAGKnowledgeSource
  → 减少 Top N 数量（N → N/2 → 1）
  → 降级：L1 overview 重排序 → L0 tags only

步骤 2：若仍超预算，压缩 ConversationHistorySource
  → 近 5 轮 → 近 3 轮 → 近 1 轮
  → 用 session 摘要替代早期轮次

步骤 3：若仍超预算，截断 MemoryRecallSource
  → 按 importance 排序，只保留高分记忆条目
```

| 策略       | 实现                                             |
| ---------- | ------------------------------------------------ |
| 知识库注入 | L0 粗筛 → L1 overview 重排序 → Top N             |
| 对话历史   | 近 5 轮完整 + 早期摘要                           |
| Token 预算 | 由 Provider 配置决定，构造时注入 ContextPipeline |

## Round 层 — messages 结构演化

### 关键决策：build() 调用一次（方案 A）

|                       | 方案 A（选定）：build() 只调用一次 | 方案 B（排除）：每轮重新 build() |
| --------------------- | ---------------------------------- | -------------------------------- |
| RAG/Memory I/O        | 单次                               | 每轮重复，代价大                 |
| 结果一致性            | 稳定                               | 可能轮次间变化                   |
| Source 职责边界       | 清晰                               | Source 需感知 round 状态         |
| tool_results 超长保护 | 输出截断守卫                       | 过度设计                         |

**tool_results 超长**由写回 messages 前的截断守卫保护，而非重新调用 Pipeline。

### round 0 → round N 的 messages 演化

```
run 开始（build() 产出 AgentContext）：

messages_0 = [
  { role: User,      content: "对话摘要：..."    },  // 若有早期摘要
  { role: User,      content: turn[N-4].user    },  // ┐
  { role: Assistant, content: turn[N-4].content },  // │ 近 5 轮完整历史
  ...                                                // ┘
  { role: User,      content: current_inbound   },  // UserMessageSource 注入
]

round 0 完成（LLM 返回 ToolCall，工具执行完毕）：

messages_1 = messages_0 + [
  { role: Assistant, content: [
      Text("我来帮你查一下..."),
      ToolUse { id: "tu_1", name: "search_content", input: {...} },
      ToolUse { id: "tu_2", name: "filesystem",     input: {...} },
  ]},
  { role: User, content: [
      ToolResult { tool_use_id: "tu_1", content: "搜索结果..." },
      ToolResult { tool_use_id: "tu_2", content: "文件内容..." },
  ]},
]

round 1 完成（LLM 返回纯文本，无 ToolCall → run 结束）：

messages_2 = messages_1 + [
  { role: Assistant, content: [Text("根据结果，...")] },
]
```

**ToolResult 位置**：依照 Claude/OpenAI API 格式，tool_results 作为 `role: User` 的 content blocks，而非独立消息角色。

**`RoundStarted.message_count`**：反映本轮实际发送给 Provider 的 `messages` 数组长度，随 round 数线性增长，供 Observer 监控 context 规模。

## 关键设计决策

| 决策                             | 选择                                        | 理由                                                               |
| -------------------------------- | ------------------------------------------- | ------------------------------------------------------------------ |
| build() 调用时机                 | 每次 run 调用一次（round 0 前）             | RAG/Memory I/O 代价大；tool_results 由截断守卫保护                 |
| system_prompt vs messages 分离   | Source 按注入目标分流                       | 对齐 Provider ChatRequest 结构；知识是指令背景，历史是对话轨迹     |
| ContextInput 不可变              | run 级快照，构造后只读                      | AgentLoop 对 round 透明；避免 round 间状态污染                     |
| 历史压缩时机                     | compressed_history() 同步执行，摘要异步生成 | 主流程不阻塞；摘要有滞后一轮的容忍                                 |
| fragments 不传 Provider          | 仅用于 Observer                             | Provider 接口干净；审计通过 AgentEvent 而非 API 参数               |
| SoulSource 与 IdentitySource 拆分 | SoulSource(p=0) 固定核心，IdentitySource(p=1) 按 mode 路由 | SOUL 是不变人格，IDENTITY 是场景化行为；拆分避免路由逻辑污染核心层 |
| RuntimeContextSource 独立 Source | p=2，无依赖，inject 时生成 | 时间/语言是运行时事实，与身份无关；独立 Source 方便测试和 mock |
