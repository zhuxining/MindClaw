# Observability — Runtime 可观测性

---

## § 职责定位

Observability 子系统负责收集、存储和展示 Agent Runtime 的关键指标与调试信息，不负责业务执行决策。

---

## § 核心原则

**分层可观测**：用户层、日志层、指标层、调试层分离。

**覆盖完整 runtime**：观测点不只来自 `RunHooks`，还包括 Loop、ToolExecutor、AgentSpawnDispatcher 和 Provider Adapter。

---

## § 输入与输出

**输入**：Loop 事件、Runner 事件、Provider 事件、工具执行结果、spawn 状态变化。

**输出**：UI 实时状态、结构化日志、指标记录、调试快照。

---

## § 核心实体

**ObservabilityCollector**：可观测事件的统一分发中心。

**RuntimeEvent**：运行时事件。
关键属性：事件类型、时间戳、Session/Run ID、负载。

**MetricsStore**：指标持久化存储。

---

## § 观测点

建议至少覆盖四个观测面：

- Loop：session queue、run 构建、取消、持久化
- Runner：iteration 次数、stop reason、usage
- Tool：工具成功率、耗时、超时
- Spawn：派生次数、等待时间、后台完成率

---

## § 四层可观测架构

```text
用户层
-> 当前状态、工具时间线、后台任务通知

日志层
-> 结构化 runtime events

指标层
-> token / latency / tool success / spawn completion

调试层
-> spec snapshot / provider raw response / full message chain
```

---

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| 观测事件是否只来自 RunHooks？ | 否，Loop/Runner/Tool/Spawn 都发事件 | 只在 Hooks 中采集 | 新架构中 spawn 与 Loop 编排都是一级语义，不能只靠 Hooks 覆盖 |
| 观测模型是否分层？ | 是，用户/日志/指标/调试四层 | 只写日志 | 不同受众需要不同粒度，统一日志无法同时满足 UI 与排障 |
