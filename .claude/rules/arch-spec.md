# 架构设计与文档规范

> 本规范适用于任何软件系统的架构设计与文档撰写。  
> 规范同时作为 Agent 可执行的规则集使用——每条规则均标注 **REQUIRED** / **PROHIBITED** / **OPTIONAL**，Agent 可机械地对照执行与自检。

---

## Part 1：术语表

本规范中所有术语以此定义为准，Agent 和人均使用同一词汇：

| 术语 | 定义 |
|------|------|
| **Module（模块）** | 拥有单一变更理由的代码/逻辑单元 |
| **Boundary（边界）** | 两个模块之间的接口契约；跨越边界必须通过显式接口 |
| **Entity（实体）** | 具有业务身份、生命周期独立的核心对象，不等同于所有数据模型 |
| **Constraint（约束）** | 不可违背的限制，违背导致系统失效或违规 |
| **Principle（原则）** | 指导决策的价值取向，可在权衡中排定优先级 |
| **Decision（决策）** | 在多个可行方案中的有意选择，必须记录理由 |
| **Service（服务）** | 无状态的业务逻辑单元，接受输入、产生输出、不持有可变状态 |
| **Flow（流程）** | 跨多个模块/实体的端到端执行路径，描述系统如何响应一个触发事件 |
| **ADR** | Architecture Decision Record，单条设计决策的结构化记录 |
| **Overview Doc（总览文档）** | 从全局视角描述整个系统或子系统的设计文档 |
| **Sub-module Doc（子模块文档）** | 围绕单一模块职责展开的设计文档 |
| **Reference Doc（参考文档）** | 描述客观现状的文档（如代码目录结构），随代码变化而更新 |

## Part 2：触发条件

### 2.1 何时必须新建架构文档

满足以下任一条件时，**REQUIRED** 新建或更新对应架构文档：

- 新系统或新子系统从零开始设计
- 引入新的跨模块边界（新增 Module 且对外暴露接口）
- 核心实体的定义或关系发生变更
- 单次变更影响 ≥ 3 个模块
- 安全边界发生变更（信任模型、权限模型、加密方案）

### 2.2 何时不需要架构文档

以下变更 **PROHIBITED** 触发架构文档更新（避免过度文档化）：

- 单模块内的实现优化，未改变接口契约
- Bug 修复，不涉及接口变更
- 配置参数的调整
- 测试代码的修改

### 2.3 何时更新已有文档

满足以下任一条件时，**REQUIRED** 更新已有文档：

- 对应模块的边界（接口契约）发生变更
- 文档中记录的设计决策被推翻
- 核心实体新增或删除

## Part 3：设计方法

### 3.1 边界识别

边界划分是架构设计的核心工作。判断两个功能是否应在同一 Module 内，依据以下维度：

**正确的划分依据：**

1. **变更理由一致性**：同一原因驱动变更的代码放在同一 Module。若 A 和 B 总是因为不同原因同时改动，它们属于不同 Module。
2. **数据所有权**：每份数据只有一个 Module 拥有写权限。哪个 Module 创建并维护这份数据，边界就在哪里。
3. **部署独立性**：可以独立部署的单元天然构成边界。
4. **信任级别**：不同信任域（如用户输入 vs 系统内部、外部 API vs 内部服务）之间必须有显式边界。

**PROHIBITED 的划分方式：**

- 按功能"看起来相似"划分——相似不代表同一变更理由
- 按技术分层划分（如 controller / service / repository 各为一个 Module）——这是实现结构，不是业务边界
- 按代码文件数量或行数均分

**边界的表达方式：**

边界通过显式接口（函数签名、trait、API 契约）表达，**PROHIBITED** 通过共享全局状态或直接访问另一 Module 的内部数据跨越边界。

---

### 3.2 实体建模

#### 什么是核心实体

满足以下全部条件的对象才是核心实体，**REQUIRED** 在架构文档中描述：

- 出现在 ≥ 2 个关键 Flow 中
- 拥有独立的生命周期（可被创建、修改、删除）
- 承载系统的核心业务语义（去掉它系统无法运行）

以下对象 **PROHIBITED** 列为核心实体：

- 配置参数
- 中间计算结果
- 仅在单个 Flow 内使用的临时对象
- 事件/消息（除非系统对其持久化并有查询需求）

#### 实体描述格式

**REQUIRED** 按以下格式描述每个核心实体：

```
**[实体名]**：[一句话说明它代表什么业务概念]。
关键属性：[属性1的语义]、[属性2的语义]、[属性3的语义]。
关系：[与其他实体的关系，使用"包含/属于/引用"等业务词汇]。
```

**PROHIBITED** 在实体描述中写：字段的数据类型、数据库列名、序列化格式、默认值。

#### 实体关系图要求

- **REQUIRED** 使用 Mermaid ER 图或关系列表表示实体关系
- **REQUIRED** 关系标注业务语义（如"一个用户拥有多个会话"），而非数据库外键名称
- **REQUIRED** 只画核心实体，通常 3 ~ 8 个
- **PROHIBITED** 在实体关系图中展示字段列表

---

### 3.3 设计决策记录（ADR）

每个值得记录的设计决策使用以下 4 列表格格式：

| 决策问题 | 选择 | 放弃的替代方案 | 理由 | 变更条件（可选）|
|---------|------|--------------|------|----------------|

字段说明：

- **决策问题**：用疑问句描述面临的选择（如"消息存储用 SQLite 还是文件系统？"）
- **选择**：明确选定的方案
- **放弃的替代方案**：至少列出一个被否定的方案
- **理由**：为什么选这个、不选替代方案
- **变更条件**：什么情况下这个决策应该被重新审视（可不填）

**REQUIRED**：每个 ADR 必须包含前 4 个字段。  
**PROHIBITED**：决策记录中写实现细节、代码示例、参数配置。

## Part 4：文档规范

### 4.1 文档分类

架构文档分为两类，性质不同、规范不同：

| 类型 | 定义 | 示例 |
|------|------|------|
| **设计文档** | 记录架构意图、原则、决策；时效性强，反映"为什么" | `00-overview.md`、`03-agent-core.md` |
| **参考文档** | 描述客观现状，随代码变化；反映"是什么" | `directory-structure.md`、数据库表结构索引 |

两类文档 **PROHIBITED** 混放在同一目录层级。  
参考文档 **REQUIRED** 放在 `reference/` 子目录。

---

### 4.2 总览文档（Overview Doc）

**定位**：从全局视角描述整个系统或子系统，是架构文档的入口。每个系统只有一个总览文档。

**REQUIRED 章节（按顺序）**：

#### § 系统目标与约束

- 一句话描述系统是什么、为谁服务
- 列出核心约束（**REQUIRED** 每条约束可验证——能回答"是否满足"）
- **PROHIBITED**：路线图、版本计划、"未来考虑"

#### § 核心设计原则

- 3 ~ 5 条，每条包含：名称 + 一句规则描述 + 一句理由
- **REQUIRED** 原则应能指导子模块的具体决策
- **PROHIBITED**：超过 5 条、无理由的原则

#### § 关键设计决策

- 使用 Part 3.3 的 ADR 表格格式
- 仅列影响全局的决策，3 ~ 7 条
- **PROHIBITED**：单个模块内部的决策（归属对应子模块文档）

#### § 边界划分

- 用 ASCII 图或层级列表展示主要模块/层
- **REQUIRED** 每个模块一句话说明职责
- 箭头表示数据流方向
- **PROHIBITED**：展示调用栈细节、方法名、参数列表

#### § 核心实体关系

- 按 Part 3.2 的格式描述每个核心实体
- **REQUIRED** 使用 Mermaid ER 图展示实体关系
- **PROHIBITED**：字段列表、类型定义

#### § 整体流程

- 1 ~ 2 个端到端主路径，使用编号步骤，每步一句话
- **PROHIBITED**：异常路径、边缘 case、错误处理步骤

**OPTIONAL 章节**（仅在系统有明确需求时添加）：

- **部署架构**：描述运行时进程拓扑、部署方式
- **安全架构**：描述信任边界、权限模型、密钥管理方式

**篇幅控制**：总览文档 **200 ~ 400 行**。超出说明内容越界，必须将具体内容移至子模块文档。

---

### 4.3 子模块文档（Sub-module Doc）

**定位**：围绕单一模块职责展开，解释"这个模块做什么、为什么这样做"。

**REQUIRED 章节（按顺序）**：

#### § 职责定位

格式固定：`[模块名] 负责 [做什么]，不负责 [不做什么]。`

- **REQUIRED** 包含"不负责什么"——这是边界声明，不可省略
- 字数 ≤ 60 字
- 这句话应能回答："我该往哪个模块加这个功能？"

#### § 核心原则（OPTIONAL）

- 本模块特有的、补充全局原则的约束，≤ 3 条
- 若本模块无额外约束，省略此节

#### § 边界与实体

**REQUIRED** 包含以下三项：

- **输入**：接收什么（接口名称 + 一句语义说明）
- **输出**：产生什么（接口名称 + 一句语义说明）
- **核心实体**：本模块管理的实体，按 Part 3.2 格式描述

**PROHIBITED**：字段详细列表、序列化格式、数据库 schema

#### § 关键流程

- 描述本模块的主执行路径，使用编号步骤，每步一句话，≤ 7 步
- **PROHIBITED**：异常处理步骤、错误路径、重试逻辑

图表选择优先级（从高到低）：

1. 文字编号步骤——能用就用
2. Mermaid Sequence Diagram——用于跨模块交互
3. Mermaid State Diagram——用于状态转换密集的模块

#### § 设计决策与权衡

- 使用 Part 3.3 的 ADR 表格格式，范围限于本模块
- **REQUIRED**：每个 ADR 必须有"放弃的替代方案"
- 这是子模块文档中最重要的节——记录"为什么"，而非"是什么"

**篇幅控制**：子模块文档 **100 ~ 250 行**。超出说明需要拆分，或内容越界至实现层面。

---

### 4.4 参考文档（Reference Doc）

**定位**：描述客观现状，不记录设计意图。典型例子：代码目录结构、数据库表索引。

**规则：**

- **REQUIRED** 只描述当前状态，不写"为什么这样组织"
- **REQUIRED** 代码重组时同步更新，无法保持同步则删除
- **PROHIBITED** 写设计决策、设计原则
- **PROHIBITED** 放在设计文档目录中（必须在 `reference/` 子目录）

---

### 4.5 目录结构与命名

**REQUIRED** 目录结构：

```
docs/design/architecture/
├── 00-overview.md              # 总览文档（唯一，不按版本拆分）
├── NN-kebab-case.md            # 主题子模块文档（NN = 两位数字，表示阅读顺序）
├── NN.MM-kebab-case.md         # 子文档（MM = 子序号）
└── reference/
    ├── directory-structure.md  # 参考文档
    └── ...
```

**命名规则：**

- 文件名全小写，单词间用连字符 `-` 分隔
- 数字编号仅表示阅读顺序，不表示版本
- **PROHIBITED** 使用 `v1/`、`v2/`、`old-` 等版本前缀目录——版本通过文档状态标注表达
- **REQUIRED** 同一主题只允许一个 `active` 文档存在

## Part 5：写作规则

### 5.1 文档状态标注

**REQUIRED** 每个文档头部包含状态标注：

```markdown
> **Status**: `active` | `deprecated` | `draft`
> **Superseded by**: [链接]（仅 deprecated 文档填写）
```

**规则：**

- `deprecated` 文档 **REQUIRED** 指向替代文档；若 30 天内无替代文档，应删除
- `draft` 文档 **PROHIBITED** 出现在主 README 导航中
- **PROHIBITED** 无状态标注的文档长期存在

---

### 5.2 语言精确性

**PROHIBITED 使用的模糊词汇：**

> 可能、一般来说、通常、大概、某些情况下、等等、以此类推、视情况而定

**REQUIRED 写作格式：**

- 以系统/模块为主语，使用主动语态
- 每个约束是可验证的陈述（能回答"是否满足"的是/否问题）
- 每个原则包含：名称 + 规则描述 + 理由
- 每个决策包含：选了什么 + 没选什么 + 理由

**示例对比：**

| 禁止 | 要求 |
|------|------|
| "该模块通常负责处理用户请求" | "该模块接收用户请求，验证权限，转发至对应 Service" |
| "数据可能存储在多个地方" | "数据存储在 X 模块；Y 模块通过 X 的接口读取，不直接访问存储" |
| "考虑到性能等因素" | "选择内存缓存而非磁盘缓存，理由是读取延迟需低于 10ms" |

---

### 5.3 代码与图表规则

**代码规则：**

- **PROHIBITED** 在架构文档中写伪代码、算法实现、控制流代码
- **OPTIONAL** 接口契约可用语言无关的类型签名表示（如 `fn process(input: Request) -> Response`），单块 ≤ 10 行
- **PROHIBITED** 在类型签名中写方法体、错误处理、日志调用

**图表规则：**

| 使用场景 | 图表类型 |
|---------|---------|
| 模块/层边界划分 | ASCII 层级图 |
| 跨模块请求/响应交互 | Mermaid Sequence Diagram |
| 核心实体关系 | Mermaid ER Diagram |
| 状态转换密集的模块 | Mermaid State Diagram |
| 部署/进程拓扑 | ASCII 图或文字描述 |

**REQUIRED** 优先使用文字步骤，图表仅在文字无法清晰表达时使用。

---

### 5.4 内容边界

下表定义哪些内容属于架构文档，哪些属于实现文档：

| 内容类型 | 架构文档 | 实现文档 |
|---------|---------|---------|
| 模块职责定义 | REQUIRED | 可选 |
| 接口契约（类型签名）| 可选 | REQUIRED |
| 核心实体语义描述 | REQUIRED | 可选 |
| 设计决策与理由 | REQUIRED | 可选 |
| 算法步骤（> 3 步）| PROHIBITED | REQUIRED |
| 具体参数值/阈值 | PROHIBITED | REQUIRED |
| 异常处理路径 | PROHIBITED | REQUIRED |
| 代码实现 | PROHIBITED | REQUIRED |
| 测试用例/场景 | PROHIBITED | REQUIRED |

## Part 6：自检清单

Agent 在生成或审查架构文档后，**REQUIRED** 对照以下清单逐项检查。每项答案为是/否，否则不通过。

### 6.1 总览文档自检

- [ ] 包含一句话系统描述？
- [ ] 每条约束可验证（能回答是/否）？
- [ ] 每条设计原则包含理由？
- [ ] 边界图中每个模块有一句话职责说明？
- [ ] 核心实体有语义说明，无字段列表？
- [ ] 整体流程只包含主路径，无异常路径？
- [ ] 文档不包含：算法步骤、具体参数值、错误处理逻辑？
- [ ] Status 标注存在？
- [ ] 篇幅在 200 ~ 400 行？

### 6.2 子模块文档自检

- [ ] 职责定位包含"不负责什么"？
- [ ] 每个输入/输出有语义说明（不只是类型名）？
- [ ] 关键流程只有主路径，步骤 ≤ 7？
- [ ] 每个设计决策包含"放弃的替代方案"？
- [ ] 文档不包含：错误处理步骤、算法细节、配置参数值？
- [ ] Status 标注存在？
- [ ] 篇幅在 100 ~ 250 行？

### 6.3 写作质量自检

- [ ] 无禁用模糊词汇？
- [ ] 所有约束以主动语态陈述？
- [ ] 无伪代码（仅允许接口类型签名，且单块 ≤ 10 行）？
- [ ] 无版本子目录（`v1/`、`v2/` 等）？
- [ ] 同一主题只有一个 `active` 文档？

## Agent 执行工作流

Agent 处理架构文档任务时，遵循以下工作流：

```
1. 判断触发条件（Part 2）
   ├── 不满足触发条件 → 不需要写/更新文档，结束
   └── 满足触发条件 → 继续

2. 判断文档类型（Part 4.1）
   ├── 设计文档
   │   ├── 全局视角 → 总览文档（Part 4.2）
   │   └── 单模块视角 → 子模块文档（Part 4.3）
   └── 客观现状 → 参考文档（Part 4.4）

3. 按对应章节结构写作
   ├── 遵守语言精确性规则（Part 5.2）
   ├── 遵守代码与图表规则（Part 5.3）
   └── 遵守内容边界规则（Part 5.4）

4. 执行自检清单（Part 6）
   ├── 所有项通过 → 输出文档
   └── 存在未通过项 → 修正后重新检查
```
