# Memory — 后台提取与升华

---

## § 职责定位

Memory 子系统负责从已完成的 Turn 中提取记忆、将高价值记忆升华为知识草稿，并以后台任务方式运行；不负责前台对话编排或即时模型调用。

---

## § 核心原则

**提取先于压缩**：Turn 的记忆提取必须在该 Turn 被压缩前完成。

**后台不阻塞前台**：MemoryProcessor 和 MemorySublimationJob 通过 `InvocationMode=detached` 的后台运行模型执行，不与主对话抢同一条用户响应链。

---

## § 边界与实体

**输入**：已完成 Turn、用户确认/拒绝信号、后台任务调度事件。

**输出**：Memory 条目、KnowledgeDraft、正式 Note、后台完成通知。

**核心实体**：

**Memory**：Agent 对用户的一次观察记录。
关键属性：类别、内容、重要性、来源 Turn ID、衰减系数。

**KnowledgeDraft**：升华候选生成的待审核知识草稿。
关键属性：标题、内容、标签、来源 Memory 列表、审核状态。

---

## § 两条写入路径

### 路径 A：显式写入

LLM 在 run 中主动调用 `create_memory` 工具，直接写入 MemoryStore。

### 路径 B：自动提取

```
SessionManager.append_turn(turn)
    │
    └── AgentSpawnDispatcher.spawn(background-memory-extractor)
              │
              ├── 规则层过滤
              └── AgentRunner.run(extraction_spec, BackgroundRunHooks)
                      → MemoryStore.write_batch()
                      → 触发升华检查
```

---

## § 记忆升华流程

当待升华候选达到阈值时：

1. 后台任务查询高重要性候选
2. 使用 `AgentRunner` 生成草稿
3. 写入 `KnowledgeDraft`
4. 通过消息总线通知用户审核
5. 审核通过后写入正式笔记

---

## § 与 Runtime 的关系

- 前台 turn 完成后，由 AgentLoop 触发 Memory 后台流程
- 后台提取与升华由 AgentSpawnDispatcher 调度
- 真正的 LLM 执行仍然复用同一个 AgentRunner

因此 Memory 不需要第二套“后台 runner”，只需要后台 invocation mode。

---

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| 记忆提取如何执行？ | 作为后台 Agent 运行 | 单独造一个专用执行引擎 | 统一 spawn 调度模型，降低系统复杂度 |
| 提取是否阻塞前台？ | 否 | 在 append_turn 后同步提取 | 记忆是优化链路，不应拉长用户感知延迟 |
| 升华是否直接写正式知识？ | 否，先产出草稿 | 自动落库 | 需要保留用户审核权，避免错误知识进入长期存储 |
