> **Status**: `active`

# Context Building — 三层上下文架构

> **核心命题**：记忆是 Agent 的，知识是共同的。

---

## § 职责定位

ContextPipeline 负责将多个上下文来源按稳定性分层组装为发送给 LLM 的消息列表，不负责上下文来源的数据存储、向量检索或 RAG 实现。

---

## § 核心原则

**稳定性分层**：上下文按变化频率分为三层，稳定的内容放前层（可复用 LLM KV-cache），变化的内容放后层，避免不必要的 cache miss。

**记忆与知识分离**：记忆（Memory）是 Agent 私有的观察记录，知识（Knowledge）是人机共有的笔记。两者均在 Dynamic 层注入，但来源、所有权和升华路径不同。

---

## § 边界与实体

**输入**：`InboundMessage`（用户当前输入和会话标识）+ 各 ContextSource 实现（在初始化时注入）。

**输出**：有序的 `Vec<Message>` 消息列表，直接用于填充 AgentRunSpec.messages（不含历史 Turn，历史 Turn 由 AgentLoop 单独插入）。

**核心实体**：

**ContextSource trait**：单个上下文来源的接口契约，声明所属层级和注入优先级。
关键属性：层级（Core / Dynamic / User）、优先级数值（同层内决定注入顺序）。
关系：多个 ContextSource 实例由 ContextPipeline 持有，按层级和优先级顺序调用 `inject()`。

**CoreLayerCache**：Core 层（第一层）内容的内存缓存，存储上次构建的系统消息。
关键属性：缓存内容（SOUL.md、USER.md、AGENTS.md、工具 Schema 合并后的系统消息）、最后更新的文件修改时间戳。
关系：由 ContextPipeline 持有；引导文件（SOUL.md 等）未修改时直接返回缓存，修改后重建并更新。

**BuildContext**：单次 `inject()` 调用的参数包，供 ContextSource 访问请求上下文。
关键属性：当前 Session 引用（用于 Memory 召回）、当前 InboundMessage（用于 Skills 匹配）。
关系：由 ContextPipeline 在每次构建时创建，只在本次构建生命周期内有效。

**PendingSubagentSource**：已完成子代理（`direct` 模式）结果的注入源。
关键属性：从 SessionManager 读取 `pending_subagent_results` 列表，注入后清空。
关系：属于 Dynamic 层，priority=50（最后注入，紧跟在 SkillsSource 之后）；确保子代理结果在对话上下文中可见，但不对 LLM 产生过多干扰。

---

## § 三层架构详解

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 层：Core（稳定缓存）                                   │
│                                                             │
│  SoulSource   → SOUL.md（核心人格、价值观、行为准则）        │
│  UserSource   → USER.md（用户画像、偏好设置）               │
│  AgentsSource → AGENTS.md（Agent 定义、能力描述）           │
│  ToolSchemaSource → 内置工具 JSON Schema                    │
│                                                             │
│  变化时机：引导文件修改时更新；多请求间字节级一致            │
├─────────────────────────────────────────────────────────────┤
│  第 2 层：Dynamic（每次请求变化）                            │
│                                                             │
│  IdentitySource  (priority=10) → 当前角色/身份选择          │
│  MemorySource    (priority=20) → Agent 私有记忆召回          │
│  KnowledgeSource (priority=30) → 知识笔记 RAG 检索          │
│  SkillsSource    (priority=40) → 技能摘要 + 激活的技能指令  │
│  PendingSubagentSource (priority=50) → 已完成子代理结果摘要 │
│                                                             │
│  变化时机：每次请求动态组装，不可缓存                        │
├─────────────────────────────────────────────────────────────┤
│  第 3 层：User（每次请求唯一）                               │
│                                                             │
│  RuntimeSource   → 当前时间、平台、语言                     │
│  UserInputSource → 用户输入文本 + 媒体附件                  │
│                                                             │
│  变化时机：每次请求唯一，不可缓存                            │
└─────────────────────────────────────────────────────────────┘
```

最终发送给 LLM 的消息顺序：
`[Core 系统消息] → [Dynamic 系统消息 × N] → [历史 Turn 消息] → [User 消息]`

---

## § 记忆升华机制

记忆升华是"记忆是 Agent 的，知识是共同的"这一命题的实现路径：

1. Agent 在对话中积累 Memory（Agent 私有），高 importance 的 Memory 被标记为升华候选。
2. MemoryStore 为候选记忆生成知识草稿（KnowledgeDraft），草稿暂存但不写入 vault。
3. 用户在下次会话中看到草稿提示，确认后草稿被写入 `vault/knowledge/` 成为正式 Note。
4. 此后该知识由人类直接维护，Agent 可通过 KnowledgeSource 检索，但不再自动修改。

---

## § 关键流程

1. ContextPipeline 检查 CoreLayerCache 是否有效（引导文件未修改），有效则直接使用缓存的 Core 系统消息。
2. 无效时，重新读取 SOUL.md、USER.md、AGENTS.md 和工具 Schema，构建新的 Core 系统消息，更新缓存。
3. 按优先级顺序调用各 Dynamic 层 ContextSource：MemorySource 执行向量相似度检索，KnowledgeSource 执行 RAG，SkillsSource 加载匹配的 Skills，PendingSubagentSource 读取并清空已完成子代理结果。
4. UserInputSource 将运行时上下文（时间、平台）和用户输入封装为 User 消息。
5. 返回 `[Core 消息, Dynamic 消息..., User 消息]`，由 AgentLoop 插入历史 Turn 后填入 AgentRunSpec。

**PendingSubagentSource 的特殊行为**：

- 从 SessionManager 读取 `pending_subagent_results` 列表
- 将结果格式化为系统消息注入上下文（如"[后台任务完成] 文件分析结果：..."）
- **读取后立即清空列表**，避免重复注入
- 仅注入 `direct` 模式的子代理结果；`synthesize` 模式的结果已通过 Turn 历史自然保留

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| 为什么分三层？ | Core 稳定 / Dynamic 动态 / User 唯一 | 单一系统提示词每次重新组装 | Core 层字节级稳定，LLM KV-cache 可复用，降低 token 成本；三层分离使缓存策略清晰 |
| Memory 在哪层注入？ | Dynamic 层（每次请求按相关性召回） | Core 层（固定预加载） | Agent 记忆量会随时间增长，全量预加载超过上下文窗口；按相关性动态召回保证窗口利用率 |
| Knowledge 在哪层注入？ | Dynamic 层（每次请求 RAG 检索） | 预加载全量知识到 Core 层 | 知识库持续增长，全量超过上下文限制；RAG 检索按相关性筛选，聚焦于当前请求 |
| 运行时数据（当前时间）在哪层？ | User 层（每次唯一） | Dynamic 层 | 时间信息每次请求不同；放 User 层保持 Dynamic 层内容相对稳定，不破坏 Dynamic 层的可重用性 |
| 记忆升华由谁发起？ | Agent 提议草稿，人类确认后写入 | Agent 直接写入 Knowledge | 体现"知识是共同的"——Knowledge 由人类主权；Agent 自动写入会绕过人类审查，可能引入不准确的知识 |
| 子代理结果如何注入上下文？ | PendingSubagentSource（Dynamic 层） | 不注入，依赖用户主动查询 | `direct` 模式子代理结果直接推送给用户后，需在下次对话中保留上下文引用；不注入则用户忘记查询时上下文丢失 |
| PendingSubagentSource 注入后是否清空？ | 是，读取后立即清空 | 保留多轮，由用户确认后清空 | 子代理结果已完成通知，不需持久保留；清空避免重复注入，简化状态管理；如有需要用户可显式提及 |
| Memory/Knowledge 放在 history 前还是后？ | 前（作为系统消息） | 后（紧邻 User 消息） | 放在前确保检索结果不会被截断（历史很长时）；放在后更接近标准 RAG 模式但破坏 [History]→[User] 连续性；当前设计通过表述方式建立关联 |
