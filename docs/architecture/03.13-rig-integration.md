# Rig Integration — Execution Kernel

---

## § 职责定位

本章描述 MindClaw 如何最大化复用 [rig](https://github.com/0xPlaygrounds/rig) 的 Agent、provider、streaming、tool calling 和 MCP 能力。Rig 是 run 内部的 Execution Kernel；MindClaw 仍持有业务编排与长期契约。

---

## § 当前迁移状态

| Phase | 状态 | 说明 |
|-------|------|------|
| Provider Rig 化 | ✅ 完成 | `ProviderRegistry` 只负责配置、密钥、主模型/轻量模型解析，并返回 `AgentModelSet` |
| Tool Rig 化 | ✅ 完成 | 内置工具、spawn 工具和 MCP 工具统一为 Rig `ToolDyn` |
| Runner Rig 化 | ✅ 完成 | Runner 使用 `AgentBuilder`、`StreamingPromptRequest`、`PromptHook`、`ToolSet/ToolServerHandle` |
| Loop 瘦身 | ✅ 完成 | Loop 不消费 Rig stream/message，只构建 spec、observer、tool scope 并持久化结果 |
| MCP Rig 化 | ✅ 完成 | MCP 连接由 MindClaw 管理，远端工具通过 Rig `McpTool` 暴露 |
| Extractor / dynamic_context | 🔜 后续 | ContextPipeline 仍是上下文所有者，Rig 扩展能力后续单独引入 |

---

## § 核心原则

**Rig 接管执行，不接管业务边界**：Rig 负责 model ↔ tools 多轮执行、streaming、tool result 回填和最终 history；`AgentProfile`、`AgentLoop`、`SessionManager`、`ContextPipeline`、`AgentSpawnDispatcher`、Review & Evolution 仍由 MindClaw 定义。

**Provider 选择停在配置层**：ProviderRegistry 读取主模型与轻量模型配置并创建 `AgentModelSet`；Runner 不接收 provider name，只在已解析模型集合内选择。

**工具只有 Rig 执行入口**：不再保留 MindClaw 自定义 Tool trait、ToolRegistry 或 ToolExecutor。工具权限来自 Profile 过滤，执行来自 Rig ToolServer。

**RunHooks 变成 observer**：MindClaw `RunHooks` 不驱动执行循环；`RigPromptHook` 适配 Rig `PromptHook`，负责文本增量、工具状态、取消、错误策略和 MessageBus 状态桥接。

## § Rig 能力映射

| Rig 能力 | MindClaw 使用点 | 用途 |
|---------|-----------------|------|
| `rig::providers` | `providers/registry.rs` | 创建 Anthropic / OpenAI / DeepSeek completion model |
| `rig::agent::AgentBuilder` | `agent/runner.rs` | 设置 name、preamble、context、tools、temperature、max_tokens、max_turns |
| `rig::agent::StreamingPromptRequest` | `agent/runner.rs` | 执行带 history 的 multi-turn streaming run |
| `rig::agent::PromptHook` | `agent/runner.rs::RigPromptHook` | 观测文本、工具、完成、取消和错误 |
| `rig::tool::ToolDyn` | `agent/tools/*` | 内置工具与 spawn 工具统一接口 |
| `rig::tool::ToolSet` | `agent/runner.rs` | 本次 run 的工具集合 |
| `rig::tool::server::ToolServer` | `agent/runner.rs` | 给 Rig Agent 提供工具调用 handle |
| `rig::tool::rmcp::McpTool` | `agent/tools/mcp.rs` | MCP 远端工具适配 |

---

## § MindClaw 保留边界

- `AgentProfile`：身份、模型、工具、上下文、安全、委托策略
- `AgentLoop`：消息串行化、上下文构建、tool scope 构建、结果持久化、done/status
- `ContextPipeline`：Vault / Memory / Skill 上下文所有者
- `AgentSpawnDispatcher`：inline subagent 与 detached background 编排
- `SessionManager`：turn 历史与工具轨迹持久化
- Review & Evolution：候选生命周期和审核流程

---

## § 执行链

```text
InboundMessage
-> AgentLoop
-> AgentRunSpec + tool scope + observer
-> AgentRunner
-> Rig AgentBuilder
-> StreamingPromptRequest.multi_turn()
-> Rig model/tool loop
-> AgentRunResult
-> SessionManager / MessageBus
```

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| Rig 是否成为 MindClaw 顶层 Agent？ | 否，只作为 Runner 内部执行内核 | 直接用 Rig Agent 替代 AgentProfile | MindClaw 需要自己的 Profile、Context、Session、Spawn 和 Review 契约 |
| Provider API 是否再包装 complete/stream？ | 否，ProviderRegistry 只返回 `AgentModelSet` | `LLMCompletionModel::complete()` / `stream()` 二次封装 | 执行语义集中在 Runner，避免 provider 层重新长出 execution API |
| 轻量模型未配置怎么办？ | 回退到主模型 | 强制配置或推断 fast tier | 配置语义明确，避免隐式换模型 |
| 工具循环谁负责？ | Rig `StreamingPromptRequest` 和 ToolServer | Runner 手写循环 | Rig 已内置 multi-turn tool calling 和 history 回填 |
| MCP 是否自研 Tool adapter？ | 否，使用 Rig `McpTool` | 自定义 `MCPToolAdapter` | 复用 Rig MCP 支持，MindClaw 只保留配置与连接生命周期 |
| ContextPipeline 是否改用 Rig dynamic_context？ | 暂不 | 本轮迁移上下文所有权 | 上下文是 MindClaw 业务边界，Rig dynamic_context 后续可独立评估 |
