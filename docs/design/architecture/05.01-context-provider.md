## 6.6 Context Pipeline — 可插拔上下文组装

上下文组装仍采用可插拔 `ContextSource` 管线，但其调用时机固定为：Session 解析完成、Agent Command 未命中之后，由 `run_once()` 显式触发。

### System Prompt 组装结构

```
┌─────────────────────────────────────────────────────────────┐
│ 固定层（启动时加载）                                         │
├─────────────────────────────────────────────────────────────┤
│ SOUL.md / IDENTITY.md / USER.md / Tool Schema              │
├─────────────────────────────────────────────────────────────┤
│ 动态层（每次 run 按需注入）                                  │
├─────────────────────────────────────────────────────────────┤
│ MemoryRecallSource                                          │
│ RAGKnowledgeSource                                          │
│ ConversationHistorySource                                   │
│ UserMessageSource                                           │
└─────────────────────────────────────────────────────────────┘
```

### ContextSource Trait 与 Pipeline

```rust
// src-tauri/src/agent/context_pipeline.rs

pub struct ContextFragment {
    pub role: MessageRole,
    pub content: String,
    pub token_estimate: usize,
    pub label: String,
}

#[async_trait]
pub trait ContextSource: Send + Sync {
    fn name(&self) -> &str;
    fn priority(&self) -> i32;
    fn enabled(&self) -> bool { true }
    async fn inject(
        &self, ctx: &ContextBuildContext, budget: usize,
    ) -> Result<Vec<ContextFragment>, AppError>;
}

/// 使用 Arc 而非引用：避免 async_trait + 多重借用的生命周期冲突。
/// AgentLoop 本身通过 Arc 持有这些资源，clone Arc 成本可忽略。
pub struct ContextBuildContext {
    pub inbound: InboundMessage,
    pub session: Arc<Session>,
    pub memory: Arc<MemoryManager>,
    pub services: Arc<ServiceContainer>,
    pub db: Arc<DbState>,
}

pub struct BuiltContext {
    pub system_prompt: String,
    pub messages: Vec<ChatMessage>,
    pub fragments: Vec<ContextFragment>,
}

pub struct ContextPipeline {
    sources: Vec<Arc<dyn ContextSource>>,
    total_budget: usize,
    budget_allocations: HashMap<String, usize>,
}
```

构建逻辑：按 `priority` 顺序遍历 source，在各自 budget 内注入 fragment；超预算时优先削减 RAG，再压缩历史，最后截断观察类内容。

### 内置源映射

| Source | Priority | 默认预算 | 数据来源 | 注入方式 |
|--------|----------|---------|---------|---------|
| `SystemPromptSource` | 0 | ~2K | SOUL.md + IDENTITY.md + USER.md + Tool Schema | 固定加载 |
| `RAGKnowledgeSource` | 10 | ~10K | `knowledge/` 目录 | `search_with_rerank` Top N |
| `MemoryRecallSource` | 20 | ~2K | `memories` 表 | relevance + importance 排序 |
| `ConversationHistorySource` | 30 | ~50K | session 历史 | 近 5 轮完整 + 早期摘要 |
| `UserMessageSource` | 100 | ~1K | 当前消息 | 始终最后 |

### Token 预算管理

| 策略 | 实现 |
|------|------|
| 知识库注入 | L0 粗筛 → L1 overview 重排序 → Top N |
| 对话历史 | 近 5 轮完整 + 早期摘要 |
| Token 预算 | 由 Provider 配置决定，通过 `max_tokens` 参数传入 |

## 6.7 Provider 层 — LLM 抽象

Provider 直接向 AgentLoop 产出事件流，而不是纯 token callback。这样文本增量、工具调用和结束事件都能进入统一状态机。

### ChatMessage — 支持多内容块

工具循环要求 assistant 消息同时携带文本和 tool_use 请求，tool result 作为独立消息回传。因此 `ChatMessage` 采用 content block 数组结构（与 Claude/OpenAI API 格式对齐）：

```rust
// src-tauri/src/providers/traits.rs

pub enum MessageRole {
    User,
    Assistant,
}

/// 消息内容块：文本、工具调用请求、工具执行结果
pub enum MessageContent {
    Text(String),
    ToolUse { id: String, name: String, input: Value },
    ToolResult { tool_use_id: String, content: String, is_error: bool },
}

pub struct ChatMessage {
    pub role: MessageRole,
    pub content: Vec<MessageContent>,
}
```

`ChatMessage` 的 content 为 `Vec<MessageContent>`，允许 assistant 消息同时包含 `Text` + 多个 `ToolUse`，Provider 实现负责转换为对应 API 格式（OpenAI 的 `tool_calls` 字段 / Claude 的 content blocks）。

### ChatRequest — 统一请求参数

```rust
pub enum ToolChoice {
    Auto,
    None,
    Specific(String),
}

pub struct ToolSchema {
    pub name: String,
    pub description: String,
    pub parameters: Value,  // JSON Schema
}

pub struct UsageStats {
    pub input_tokens: u32,
    pub output_tokens: u32,
}

/// 统一的 LLM 请求参数
pub struct ChatRequest<'a> {
    pub model: String,
    pub messages: &'a [ChatMessage],
    pub system: Option<&'a str>,
    pub tools: &'a [ToolSchema],          // 可用工具定义
    pub tool_choice: ToolChoice,           // 工具调用策略
    pub max_tokens: Option<u32>,
    pub cancel: CancellationToken,         // 取消令牌
}
```

### Provider trait

```rust
#[async_trait]
pub trait Provider: Send + Sync {
    async fn chat(
        &self,
        request: ChatRequest<'_>,
    ) -> Result<ProviderResponse, AppError>;

    async fn chat_stream(
        &self,
        request: ChatRequest<'_>,
    ) -> Result<Pin<Box<dyn Stream<Item = Result<ProviderEvent, AppError>> + Send>>, AppError>;

    fn supports_streaming(&self) -> bool;
}
```

**Provider 实现要求**：

- `chat_stream` 内部使用 `tokio::select!` 监听 `cancel` token，取消时 abort HTTP 请求。
- Provider 必须在内部缓冲 tool call arguments delta（OpenAI/Claude 流式 API 增量返回 JSON 片段），仅在参数 JSON 完整后才发出 `ProviderEvent::ToolCall`。
- `tools` 参数映射到对应 API 格式（OpenAI `functions` / Claude `tools`）。
- `tool_choice` 映射到 API 对应字段（OpenAI `tool_choice` / Claude `tool_choice`）。

### ProviderEvent 到 AgentLoop 的映射

| ProviderEvent | AgentLoop 动作 |
|---------------|----------------|
| `TextDelta` | 立即转成 `OutboundPayload::Chunk`，累积到 `text_buffer` |
| `ToolCall` | 累积到 `tool_calls` 列表，等 `Finished` 后批量执行 |
| `Finished` | 无 tool_calls → `PersistingTurn`；有 tool_calls → `ExecutingTools` → 下一轮 |

首期 `OpenAICompatProvider` 需完整实现 `TextDelta`、`ToolCall`、`Finished` 三种事件，支持工具循环。
