# Observability — Runtime 可观测性

---

## § 职责定位

Observability 子系统负责收集、存储和展示 Agent Runtime 的状态、日志、指标和调试信息；不负责业务审核、记忆演化判断或经验教训生成。

---

## § 核心原则

**分层可观测**：用户状态、结构化日志、指标、调试快照分离，避免一种事件同时服务所有用途。

**覆盖完整 Runtime**：观测点覆盖 Loop、Runner、RigPromptHook 工具事件、AgentSpawnDispatcher、Provider Adapter 和 Review 后台 run。

**业务审计分离**：`EvolutionLog` 解释记忆或策略变化，tracing / metrics 解释执行过程，两者不能混写。

---

## § 输入与输出

**输入**：Loop 事件、Runner 事件、RigPromptHook 流式与工具事件、spawn 状态变化、后台 run 状态变化。

**输出**：UI 实时状态、结构化日志、指标记录、调试快照。

事件命名边界：

| 名称 | 用途 |
|------|------|
| `UserVisiblePhase` | 前端或 Channel 可见的简化状态 |
| tracing spans/events | Loop / Runner / Tool / Spawn 的内部观测事件 |

---

## § 核心实体

**ObservabilityCollector**：运行时事件的统一分发中心。
关键属性：事件路由、订阅者集合、采样策略。

**Tracing events / spans**：运行期内部观测事件。
关键属性：事件类型、时间戳、Session/Run ID、负载摘要。

**MetricsStore**：指标持久化存储。
关键属性：指标名称、维度、聚合窗口、记录时间。

---

## § 观测面

| 观测面 | 关注内容 |
|--------|----------|
| Loop | session queue、run 构建、取消、持久化、review trigger |
| Runner | iteration 次数、stop reason、usage、stream 状态 |
| Tool | 工具成功率、耗时、超时、权限拒绝 |
| Spawn | 派生次数、等待时间、后台完成率 |
| Provider | 首 token 延迟、总耗时、token usage、错误类型 |
| Review run | 候选生成耗时、后台任务完成状态 |

---

## § 四层可观测架构

```text
用户层
-> 当前状态、工具时间线、后台任务通知

日志层
-> tracing events / spans

指标层
-> token / latency / tool success / spawn completion / review completion

调试层
-> spec snapshot / provider raw response / full message chain
```

---

## § 与 Review & Evolution 的边界

Observability 可以记录“某个 review run 何时开始、结束、失败、耗时多少”。

Review & Evolution 负责解释“这个 review run 为什么生成某条候选、为什么某条记忆被修正”。

因此：

- 运行期 tracing 不作为长期行为依据。
- `EvolutionLog` 不作为实时 UI 状态流。
- 两者通过 `run_id`、`turn_id` 或候选 ID 建立引用。

---

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| 观测事件是否只来自 RunHooks？ | 否，Loop/Runner/Tool/Spawn/Provider 都发事件 | 只在 Hooks 中采集 | Runtime 编排和派生执行都是一级语义 |
| 观测模型是否分层？ | 是，用户/日志/指标/调试四层 | 只写日志 | 不同受众需要不同粒度 |
| 演化记录是否并入 observability？ | 否，业务审计独立 | 把 EvolutionLog 当成日志 | 演化记录影响长期行为，不能被当成临时执行日志 |
