> **Status**: `active`

# AgentProfile — 静态定义层

---

## § 职责定位

`AgentProfile` 负责定义某类 Agent 的身份、策略和硬边界，不负责任何运行时状态、上下文组装、模型调用或工具执行。

---

## § 核心原则

**Profile 不是 Instance**：Profile 描述“应该如何运行”，不是“正在运行什么”。

**策略与状态分离**：Session、消息历史、取消状态、流式输出句柄等均属于 Runtime，不属于 Profile。

---

## § 定义来源

内置 Agent 由 `src-tauri/src/agent/agents.rs` 统一加载和注册。`agents.rs` 同时承载：

- `AgentProfile` 与各类 policy 的运行时结构
- `AgentMarkdownDefinition` / `AgentDefinitionFrontmatter` 的解析
- `AgentRegistry::bootstrap(...)` 的内置 Agent 注册入口

Main Agent 是应用固定入口，不属于可自定义 Markdown Agent。它的 profile 由 `AgentRegistry::bootstrap(...)` 在代码中创建，系统提示词仍来自 ContextPipeline / AppConfig。

Markdown Agent 只用于可派生的 SubAgent。后台执行不是独立 Agent 类型，只是委派时选择的 `InvocationMode::Detached`。内置 Markdown 文件放在 `src-tauri/src/agent/build-in/subagent/*.md`：

| 文件 | 注册 ID | 默认类型 |
|------|---------|---------|
| `subagent.md` | `subagent-inline` | SubAgent |

Markdown frontmatter 定义派生 Agent 的身份与策略，Markdown body 作为 `PromptPolicy.system_prompt_template`。如果内置 Markdown 缺失、frontmatter 解析失败、缺少 `name` / `description`，或 body 为空，启动直接失败，不使用隐藏 fallback prompt。

```yaml
---
name: subagent-inline
description: Focused delegated agent for bounded tasks.
tools:
  - read_file
model: light
maxTurns: 15
skills:
  - notes
---
```

字段规则：

- `name`：必填，内置派生 Agent 必须与注册 ID 一致。
- `description`：必填。
- `tools`：可选；省略表示继承默认工具集合。
- `model`：可选；`main` / `light` 映射到运行时主模型或轻量模型，也可填写具体模型 ID。
- `maxTurns`：可选；映射到 `ExecutionPolicy.max_iterations`。
- `skills`：可选；由上下文层预加载。

**InteractionPolicy**

定义 Agent 在不同工作域中的交互策略。模式不是人格设定，也不是情感陪伴入口；它只表达工具边界、沉淀边界和输出风格。

```rust
struct InteractionPolicy {
    default_mode: String,           // 默认模式 ID
    mode_switching: ModeSwitching,  // manual | auto | disabled
    mode_definitions: Vec<ModeDefinition>,
}

enum ModeSwitching {
    Manual,     // 用户显式切换
    Auto,       // 基于触发条件自动建议
    Disabled,   // 固定使用 default_mode
}

struct ModeDefinition {
    mode_id: String,                // 唯一标识，如 "workbench"
    name: String,                   // 显示名称
    description: String,            // 工作域说明
    system_prompt_addon: String,    // 该模式附加到 system prompt 的内容
    allowed_tools: Vec<String>,     // 该模式下允许的工具白名单（空=继承全部）
    trigger_keywords: Vec<String>,  // 自动触发关键词（mode_switching=auto 时有效）
    persistence: PersistencePolicy, // 内容沉淀边界
}

enum PersistencePolicy {
    SharedVault,     // 可保存为 Vault
    ReviewRequired,  // 只能先进入候选或审核队列
    SessionOnly,     // 仅本次会话使用，不自动沉淀
}
```

**默认模式模板**（系统提供，可覆盖）：

| 模式 ID | 名称 | 策略特征 |
|---------|------|---------|
| `workbench` | 工作台模式 | 默认协作模式，可调用知识检索、文件和工具能力 |
| `research` | 资料模式 | 面向网页、PDF 和外部文件解析，输出来源和证据 |
| `reflection` | 回顾模式 | 面向反思、复盘和记忆更新建议，默认 `ReviewRequired` |
| `vault` | Vault 沉淀模式 | 结构化输出，可生成 Vault 草稿 |
| `review` | 审核模式 | 处理观察、记忆建议和经验候选，不直接写长期状态 |

**使用方式**：

1. AgentLoop 在构建 `AgentRunSpec` 时读取当前 mode
2. 将 `system_prompt_addon` 追加到 base system prompt
3. AgentLoop 根据 `allowed_tools` 构建本次 run 的 Rig 工具范围
4. Services 根据 `persistence` 决定写入 Vault、审核候选或仅保留在会话中

## § 三类 Profile

| 类型 | 典型用途 | 默认特征 |
|------|---------|---------|
| Main | 与用户交互 | 可流式、可持久化 Session、通常允许更丰富工具 |
| Sub | 被主 Agent 同步委托 | 默认非流式、结果返回父 Agent、Ephemeral Session |
| Background | 长耗时后台任务 | `InvocationMode=detached`、异步完成、完成后独立通知 |

---

## § Profile 的使用方式

AgentLoop 每次收到消息时：

1. 通过 AgentResolver 或 mode 选出一个 `AgentProfile`
2. 读取该 Profile 的策略
3. 将 Profile 的 `system_prompt_template` 与 ContextPipeline 的 system prompt 合成 run prompt
4. 结合 Session、Context、Request Override 构建 `AgentRunSpec`
5. 交给 AgentRunner 执行

Profile 自己不执行任何逻辑。

内置 Profile 在 AppRuntime 启动时由 `AgentRegistry::bootstrap(config, main_model, light_model)` 注册。`bootstrap` 是内置 Agent 的唯一启动入口；Main Profile 在代码中固定创建，派生 Profile 从 Markdown 创建。`spawn.rs` 不再持有或生成子 Agent prompt，只按 agent id 读取 Profile。

---

## § 配置优先级

统一建议：

```text
App Defaults
< Provider Defaults
< Model Defaults
< AgentProfile Defaults
< Session Overrides
< Request Overrides
```

但只能覆盖软字段：

- `temperature`
- `max_tokens`
- `streaming`
- `reasoning_effort`

以下硬边界不可放宽：

- `allowed_tools`
- `provider_allowlist`
- `workspace_roots`
- `permission_profile`
- `max_iterations` 上限
- `cost_budget` 上限

## § 与相关模块的关系

| 模块 | AgentProfile 提供什么 | 不提供什么 |
|------|---------------------|-----------|
| AgentLoop | 构建一次 run 所需的默认策略 | Session、持久化、并发控制 |
| AgentRunner | 已解析后的执行参数来源 | 执行状态 |
| ProviderRegistry | 模型偏好与能力要求 | Provider Adapter 实例 |
| Tool scope builder | 工具白名单与超时策略 | 工具实现 |

InteractionPolicy 特别说明：

- AgentLoop 在 `resolve` 阶段确定当前 mode（用户指定或默认）
- 在 `build_context` 阶段将 mode 的 `system_prompt_addon` 注入上下文
- AgentLoop 在构建 tool scope 阶段根据 `allowed_tools` 过滤

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| Agent 是否持有 Provider？ | 否 | Agent 直接持有 `Arc<dyn Provider>` | Provider 是 adapter；Profile 只应描述模型偏好，不应绑定运行时实例 |
| Agent 是否持有 Session？ | 否 | Agent 内嵌消息历史与 turn | Session 与 Agent 生命周期不同，绑定后会污染定义层 |
| Main/Sub/Background 是否三套结构体？ | 否，共用 `AgentProfile` | 三个完全独立类型 | 差异主要是策略和 invocation mode，不值得复制整套结构 |
