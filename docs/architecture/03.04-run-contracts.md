> **Status**: `active`

# Run Contracts — 执行契约

---

## § 职责定位

Run Contracts 定义 Orchestration Layer 与 Execution Layer 之间的数据与生命周期契约，不负责具体的上下文构建、执行逻辑或持久化逻辑。

---

## § 核心对象

**AgentRunSpec**：一次 run 的冻结执行计划。

**AgentRunResult**：一次 run 的结构化结果。

**RunHooks**：Execution Layer 向外层注入生命周期副作用的接口。

**InvocationMode**：当前 run 的调用语义。

**Runtime Events**：执行过程中的共享事件契约。
包括：

- `ProviderStreamEvent`
- `RuntimeEvent`
- `UserFacingStatus`
- `RunStage`

命名分层：

| 类型 | 语义层级 | 典型消费者 |
| --- | --- | --- |
| `ProviderStreamEvent` | Provider 流协议标准化事件 | `AgentRunner` |
| `ProviderUsage` | Provider 原始 usage 统计 | Provider Adapter / `AgentRunner` |
| `RuntimeEvent` | Runtime 内部观测事件 | `observability.rs` / tracing / metrics |
| `RunStage` | Runtime 内部阶段机 | Observer / 调试状态机 |
| `UserFacingStatus` | 对外可见的简化状态 | `MessageBus` / Channel / UI |

---

## § AgentRunSpec

建议字段：

- `run_id`
- `agent_id`
- `session_id`
- `invocation`
- `resolved_provider`
- `resolved_model`
- `system_prompt`
- `messages`
- `tool_schemas`
- `max_iterations`
- `parallel_tools`
- `fail_on_tool_error`
- `streaming`
- `temperature`
- `max_tokens`
- `response_schema`
- `timeout_ms`

设计要求：

- 构建后不可变
- 包含执行所需全部上下文
- 不在执行中再做 provider/model 解析

---

## § AgentRunResult

建议字段：

- `run_id`
- `final_text`
- `full_message_chain`
- `tool_events`
- `tools_used`
- `usage`
- `stop_reason`
- `provider_metadata`

设计要求：

- 足够供 AgentLoop 完成持久化、发布、观测
- 保留完整 message chain，便于复现与调试

## § Runtime Events

`events.rs` 的定位不是业务逻辑，而是 **Agent Runtime 的共享事件协议层**。

它与 `spec.rs` 平级：

- `spec.rs` 定义 run 开始前和结束后的输入输出契约
- `events.rs` 定义 run 过程中各层传递的事件与状态契约

建议把它理解成两类协议：

**Provider → Runner 的标准化流事件**

- `ProviderStreamEvent::TextDelta`
- `ProviderStreamEvent::ToolCallReady`
- `ProviderStreamEvent::StreamFinished`
- `ProviderUsage`

作用：

- 隔离不同 Provider 的流式协议差异
- 让 `AgentRunner` 只消费统一事件，而不关心 vendor-specific SSE/JSON 格式

**Loop / Runner → Observability / Bus 的运行时事件**

- `RuntimeEvent`
- `RunStage`
- `UserFacingStatus`

作用：

- `RuntimeEvent`：供日志、指标和调试系统消费
- `RunStage`：表示内部阶段机，仅供 runtime 内部观测使用
- `UserFacingStatus`：表示前端 / Channel 可见的简化状态

命名规则：

- 凡是 `*StreamEvent`，表示流式协议中的事件片段
- 凡是 `*Usage`，表示 token 或成本统计
- 凡是 `*Event`，表示 runtime 观测事件
- 凡是 `*Stage`，表示内部阶段机
- 凡是 `*Status`，表示对外暴露的简化状态

边界要求：

- `events.rs` 适合保留为独立文件
- 不应并入 `observability.rs`，因为它不只是观测实现细节
- 不应并入 `loop_.rs` 或 `runner.rs`，因为它被多个模块共享
- 不应并入 `bus/events.rs`，因为它表达的是 runtime 内部语义，不是总线消息协议

## § InvocationMode

```text
interactive   -> 用户前台对话
inline_child  -> 同步子代理，结果回父 Agent
detached      -> 后台代理，先返回 task id
```

它影响：

- 是否流式输出给用户
- 结果交付给谁
- Session 持久化策略
- Hooks 实现选择

## § RunHooks

`RunHooks` 是 Execution Layer 的唯一业务注入点。

建议接口：

```rust
fn streaming_mode(&self) -> StreamingMode
fn on_run_start(&mut self, ctx: &RunStartContext)
fn on_iteration_start(&mut self, ctx: &IterationStartContext)
fn on_model_request_start(&mut self, ctx: &ModelRequestContext)
fn on_model_text_delta(&mut self, delta: &str)
fn on_model_response_ready(&mut self, ctx: &ModelResponseContext)
fn on_tool_batch_start(&mut self, calls: &[ToolCall])
fn on_tool_call_start(&mut self, call: &ToolCall)
fn on_tool_call_finish(&mut self, call: &ToolCall, result: &ToolResult)
fn on_iteration_finish(&mut self, ctx: &IterationFinishContext)
fn finalize_response(&mut self, content: &str) -> String
fn on_finish(&mut self, result: &AgentRunResult)
fn on_abort(&mut self, reason: &RunAbortReason)
```

建议实现：

- `InteractiveRunHooks`
- `SubAgentRunHooks`
- `BackgroundRunHooks`
- `NoopRunHooks`

---

## § 执行节点

建议将 Runner 的生命周期节点显式化：

```text
RunStart
IterationStart
ModelRequestStart
ModelTextDelta
ModelResponseReady
ToolBatchStart
ToolCallStart
ToolCallFinish
IterationFinish
ResponseFinalize
RunFinish
RunAbort
```

`RunHooks` 的方法应直接对应这些节点，而不是使用模糊的 `before_*` / `after_*` 风格命名。

---

## § 多轮迭代与多轮工具执行

多轮迭代和多轮工具执行**需要被管理**，但这项管理属于 `AgentRunner`，不属于 `RunHooks`。

建议规则：

- `AgentRunner` 负责维护 `max_iterations`、当前 iteration index、消息链增长、停止条件
- 每轮模型调用前后，Runner 触发一次 iteration 级节点事件
- 每轮若出现工具调用，Runner 触发一组 tool batch / tool call 级节点事件
- 若进入下一轮，重复上述流程

因此不需要额外设计：

- `MultiIterationHooks`
- `ToolLoopHooks`
- `RoundManagerHooks`

只需要让 `RunHooks` 在每个执行节点上重复收到带上下文的事件即可。

---

## § 上下文对象

建议为 Hooks 提供稳定的上下文值对象，而不是在方法签名中散落大量参数：

- `RunStartContext`
- `IterationStartContext`
- `ModelRequestContext`
- `ModelResponseContext`
- `IterationFinishContext`
- `RunAbortReason`

这些对象至少应包含：

- `run_id`
- `session_id`
- `agent_id`
- `invocation`
- `iteration`
- `message_count`
- `usage`
- `finish_reason`
- `tool_call_count`

---

## § StreamingMode

建议用 enum，而不是 `wants_streaming() -> bool`：

```text
Disabled
TextOnly
```

这样后续若要增加更细粒度的流式能力，不需要改 trait 语义。

## § 依赖边界

| 对象           | 由谁构建                         | 谁消费                           |
| -------------- | -------------------------------- | -------------------------------- |
| AgentRunSpec   | AgentLoop                        | AgentRunner                      |
| AgentRunResult | AgentRunner                      | AgentLoop / AgentSpawnDispatcher |
| RunHooks       | AgentLoop / AgentSpawnDispatcher | AgentRunner                      |

## § 关键流程

```mermaid
sequenceDiagram
    participant Loop as AgentLoop
    participant Hooks as RunHooks
    participant Runner as AgentRunner

    Loop->>Runner: run(spec, hooks)
    Runner->>Hooks: on_run_start
    loop 每次迭代
        Runner->>Hooks: on_iteration_start
        Runner->>Hooks: on_model_request_start
        Runner->>Hooks: on_model_text_delta
        Runner->>Hooks: on_model_response_ready
        alt 有工具调用
            Runner->>Hooks: on_tool_batch_start
            Runner->>Hooks: on_tool_call_start / finish
            Runner->>Hooks: on_iteration_finish
        else 完成
            Runner->>Hooks: finalize_response
            Runner->>Hooks: on_finish
        end
    end
    Runner-->>Loop: AgentRunResult
```

## § 设计决策与权衡

| 决策问题                        | 选择                           | 放弃的替代方案                    | 理由                                                               |
| ------------------------------- | ------------------------------ | --------------------------------- | ------------------------------------------------------------------ |
| Hooks 是否保留？                | 是，保留为 Run Contract 一部分 | 将流式和事件逻辑直接写进 Runner   | Runner 保持无业务基础设施感知，场景差异交给 Hooks                  |
| Spec 是否可变？                 | 否                             | 允许运行中修改                    | 不可变更利于测试、复现和观测                                       |
| InvocationMode 是否独立成字段？ | 是                             | 用多个布尔值拼出语义              | invocation mode 是一等概念，直接决定 child/background 行为         |
| 是否为多轮迭代单独设计新接口？  | 否                             | 为多轮再引入额外 manager/delegate | 迭代控制本就属于 Runner；对外只需暴露带 iteration 上下文的节点事件 |
