# AgentLoop — turn 级编排层

---

## § 职责定位

`AgentLoop` 负责一条入站消息从到达到完成的全部编排：Session 串行化、Profile 解析、上下文构建、run spec 生成、调用 Runner、持久化、消息分发与回顾触发信号。

---

## § 核心原则

**Session 隔离**：同一 `session_key` 的消息严格串行，不同 Session 并发执行。

**先解析，再执行**：AgentLoop 必须先解析 `AgentProfile`、模型、工具、上下文，再生成 `AgentRunSpec`，不把运行时分支下放给 AgentRunner。

**控制命令优先**：`/new`、`/stop`、`/status` 等 loop 级控制命令在编排入口处处理，不进入 run 执行。

**回顾旁路触发**：Turn 完成后，AgentLoop 只发出 Review trigger，不直接写稳定记忆、经验教训或共有知识。

---

## § 核心依赖

AgentLoop 直接持有：

- `SessionManager`
- `ContextPipeline`
- `AgentRegistry`
- `ModelRouter`
- `AgentRunner`
- `AgentSpawnDispatcher`
- `AutoCompact` — 新增：自动压缩服务
- `EventPublisher`
- `Observer`
- `ReviewTrigger`

它不应直接持有某个具体 ProviderClient。

## § AutoCompact（自动压缩历史）

当 Session 过期或消息数超限时，自动压缩历史以控制上下文大小。

### 配置字段

- `session_ttl_minutes`：Session 过期时间（默认 30 分钟）
- `compression_ratio`：压缩比例（默认 0.5）
- `max_messages`：最大消息数（默认 100）
- `check_interval_seconds`：检查间隔（默认 60 秒）

### 压缩触发条件

- 消息数超过 `max_messages`
- Session 超过 TTL 未更新

### 压缩策略

保留最近的 `compression_ratio` 比例的完整 turns，早期 turns 被丢弃或摘要化。

---

## § Checkpoint Recovery（中断恢复）

当 run 因 `/stop`、超时或崩溃中断时，恢复部分执行状态。

### 检查时机

新消息到达时，在处理前检查 `session.get_checkpoint()`，若存在则调用 `restore_from_checkpoint()`。

### 恢复流程

1. 从 `session.metadata` 读取 `RuntimeCheckpoint`
2. 将 `assistant_message`（部分输出）追加到 history
3. 将 `completed_tool_results` 追加到 history
4. 为 `pending_tool_calls` 生成错误结果：”Error: Task interrupted before this tool finished.”
5. 清除 checkpoint 和 `pending_user_turn` 标记

### 持久化时机

- 工具执行前：保存 `AwaitingTools` checkpoint
- 工具执行后：更新为 `ToolsCompleted`
- 最终响应前：更新为 `FinalResponse`

---

## § Mid-turn Injection（迭代中消息注入）

当 Session 有活跃 run 时，后续消息可注入到当前迭代循环。

### SessionSlot 扩展字段

- `queue`：等待处理的消息队列
- `active_run`：当前活跃的 run
- `injection_queue`：Mid-turn 注入队列（新增）

### 注入机制

当前为基础框架，完整实现需要扩展 rig 的 Agent 循环：

1. 消息到达时检查 `active_run`
2. 若有活跃 run：普通消息进入 `queue`，注入消息进入 `injection_queue`
3. Runner 在 iteration 间隙检查 `injection_queue`
4. 将注入消息转换为 user message，追加到当前对话

### 当前状态

`injection_queue` 字段已添加，完整注入逻辑需要 rig 扩展支持。

## § 编排模型

```text
InboundMessage
    │
    ▼
resolve session / route agent
    │
    ▼
check checkpoint / restore if needed
    │
    ▼
check auto_compact / compress if needed
    │
    ▼
┌──────────────────────────────────────┐
│ Session Lock                          │
│ +                                     │
│ Global Concurrency Gate               │
└──────────────────────────────────────┘
    │
    ▼
build spec -> runner.run()
```

## § 关键流程

```text
dispatch() -> priority command?
    │
    ├── yes -> handle immediately
    │
    └── no
         │
         ▼
    acquire session lock
         │
         ▼
    load/create session
         │
         ▼
    check checkpoint -> restore if exists
         │
         ▼
    check auto_compact -> compress if needed
         │
         ▼
    resolve AgentProfile
         │
         ▼
    build context
         │
         ▼
    resolve profile model + build tool scope
         │
         ▼
    build AgentRunSpec
         │
         ▼
    AgentRunner.run(spec, tool_scope, observer, cancel)
         │
         ▼
    persist result / emit output / publish review trigger
```

## § LoopCommand 与控制面

Loop 级命令不属于 `RunHooks`，而属于 AgentLoop 的控制面。

建议统一抽象为：

- `LoopCommand::NewSession`
- `LoopCommand::StopActiveRun`
- `LoopCommand::Status`

这些命令在进入 run 之前就被 AgentLoop 拦截和处理。

建议作用域：

- `/new`：Session 级命令
- `/stop`：Run 级命令
- `/status`：Session 级命令

---

## § 中途新消息与 InterruptionPolicy

当某个 session 已经有 active run 时，再收到一条新的普通用户消息，不把它视为命令，而视为 loop 的中断策略问题。

建议定义：

```text
QueueBehindActive
CancelAndAppend
ForkNewSession
```

MindClaw 默认采用：

```text
InterruptionPolicy = QueueBehindActive
```

这个默认值在桌面端和 bot 通道上保持一致，避免用户在不同入口面对不同中断语义。

---

## § 默认行为

**`/stop`**

- 命中当前 session 的 active run
- 触发 cancel token
- 当前 run 以 `Cancelled` 结束
- 若有 checkpoint，恢复部分状态
- 不进入普通消息队列

**`/new`**

- 若当前 session 有 active run，先取消该 run
- 创建新 session
- 后续消息切换到新 session

**中途新消息**

- 若当前 session 有 active run，则进入队尾
- 当前 run 正常完成后，再消费下一条新消息

## § Partial Output

当 run 因 `/stop` 或其他控制面原因中止时，已经流出的半截输出默认不作为正式 assistant turn 落入标准会话历史。

建议处理为：

- 正式 session history 只保留完成的 assistant turn
- partial output 如需保留，应作为 runtime/debug artifact 单独记录
- 若有 checkpoint，恢复时将 partial output 作为中断标记

这样可避免会话历史被半截回答污染。

---

## § AgentLoop 如何使用 AgentProfile

Loop 不调用 Profile 的”方法”，而是读取 Profile 的定义来组装本次 run：

1. 读取 `PromptPolicy`
2. 读取 `ModelPolicy`
3. 读取 `ToolPolicy`
4. 读取 `ContextPolicy`
5. 读取 `ExecutionPolicy`
6. 读取 `SecurityPolicy`

也就是说，Loop 使用的是 AgentProfile 的配置，而不是一个运行中的 Agent 实例。

---

## § 与 AgentSpawnDispatcher 的关系

当主 Agent 触发：

- `delegate_to_agent`
- `spawn_background_agent`

AgentLoop 并不直接执行派生逻辑，而是委托给 `AgentSpawnDispatcher`：

- inline subagent：等待结果并回填给父 Agent
- detached：立即返回 task id，稍后单独通知

## § Turn 完成后的回顾触发

AgentLoop 在完成一次正常 turn、取消 turn 或工具失败 turn 后，向 Review & Evolution 发出轻量触发信号。

触发信号包含：

- `session_id`
- `turn_id`
- `run_id`
- 用户输入摘要
- Agent 输出摘要
- 工具结果摘要
- 失败、取消或用户纠正标记

AgentLoop 不判断这些信号是否应该成为记忆或经验教训。后续处理由 Review & Evolution 负责：

1. 生成 `ReviewItem`
2. 可选调度后台 review run
3. 等待用户确认或拒绝
4. 将确认后的记忆更新交给 Memory
5. 将确认后的经验教训保存为 Markdown 知识草稿

这样可以保证主调用链只负责完成用户当前请求，不被长期状态维护逻辑污染。

## § 设计决策与权衡

| 决策问题 | 选择 | 放弃的替代方案 | 理由 |
|---------|------|--------------|------|
| AgentLoop 是否直接调 ProviderClient？ | 否，通过 `AgentRunner` | Loop 直接做 LLM 调用 | 保持 turn 编排和 run 执行解耦 |
| Agent 解析放在什么时候？ | 构建 Spec 前 | 交给 Runner 或 Provider 层处理 | Profile、模型、工具、上下文都属于编排阶段决策 |
| 派生执行调度放在哪？ | `AgentSpawnDispatcher` | 塞进 Loop 主流程 | spawn 语义单独演进，避免 Loop 过胖 |
| Turn 后回顾由谁处理？ | Loop 只发触发信号，Review & Evolution 持有候选生命周期 | Loop 直接写 Memory 或知识草稿 | 回顾是长期状态审核流程，不属于 turn 编排 |
| 压缩由谁触发？ | `AutoCompact` 服务在消息处理前检查 | Runner 或 SessionManager 内部处理 | 压缩是编排层决策，不影响执行引擎 |
| Checkpoint 存储位置？ | `AgentSession.metadata` | 单独的 checkpoint 表或文件 | metadata 是运行时状态的自然存储位置 |
| Mid-turn Injection 实现层级？ | Loop 层（需 rig 扩展） | Runner 层 | 注入涉及 Session 和消息路由，属于编排 |
